### §116.10 `write_corpus` 的「补训越成功、语料越少」反向激励
`eval113.write_corpus` 原文：
```python
ok = lambda r: sum(1 for t in (r or {}).get('turns', []) if not t.get('violations'))
use = p2 if (p2 and ok(p2) > ok(base)) else base
```
`ok()` 是**绝对合规轮数**，补训 4 轮 vs 基线 48 轮 ⇒ 48 轮天然碾压。
唯一例外：`asgore` 基线 48 轮**全部违规**（ok=0），补训 4/4 合规 ⇒ `4 > 0` 成立
⇒ **48 轮语料被换成 4 轮，语料总数从 3,696 掉到 3,652**。
即「补训越成功，SFT 语料越少」—— 最不该有的反向激励。
修：只有**轮数相同**（同一份剧本）才允许替换；否则一律保留基线。
锁：`check_patch113t` 的 **T8a**（逐人：语料条数 == 主记录里非空回答数）+ **T8b**（总数 > 3000）。

### §116.11 报告表格的「分子分母不同源」
`summarize()` 里：
```python
before = per_char[nid]['violations']          # 违规**处数**
now    = sum(1 for t in p2.turns if t.violations)   # 违规**轮数**
# 渲染时两边都拿 v['turns']（=补训的 4 轮）当分母
```
两个不同量纲共用分母 ⇒ 会印出「补训前 6/4 轮」这种数学上不可能的数。
修：两边统一成「不合规轮数 / 各自总轮数」，并额外给 `before_rate` / `after_rate`。
★ 通用形态：**一个分数里，分子和分母必须来自同一个测量**。


### §116.12 合并**不幂等**：ralsei 的补丁在 158 ⇄ 160 之间 2-循环
`eval113.merge_text` 原来按 `keep + extra`（旧独有句在前、本轮新句在后）拼，再由
`cap_patch` **从尾部**裁自动句。实测（`probe2` 连续迭代）：
```
第1步 merge→158   第2步 merge→160   第3步 merge→158  …  永不收敛
```
连跑三次 `eval113`，写进产品的 `_index.json` 出现**两个不同 sha1**
（`432ff0a2…` / `a2c5618f…`）——**同一份输入，每次产出不同的产品数据**，而且不报任何错。

机制：`ralsei` 的「名字规则」2 句是**手写**（`_is_auto_sent` 为假 ⇒ `cap_patch` 不裁），
加上 2 句模板共约 180 字，而上限 `PATCH_MAX_CHARS=160` 只装得下「2 手写 + 1 模板」。
旧顺序下"保留哪一句模板"取决于**旧值里恰好有哪一句** ⇒ 每轮换一个 ⇒ 2-循环。

修：顺序改成 `list(new_s) + keep`（本轮在前、旧独有追加在后）⇒ 保留哪句**只由本轮输入决定**
⇒ 同一 new 必得同一结果。实测连跑三次 sha 恒为 `cd94956b…`。
锁：`check_patch113t` 的 **T9a**（4 个起点验 `merge(merge(x))==merge(x)`）+
**T9b 负控制**（复刻旧顺序，必须 4/4 都不收敛，否则 T9a 恒真）。

★ 通用形态：**凡是"读旧值→算新值→写回旧值所在位置"的流水线，必须验证 f(f(x))==f(x)**。
  不幂等不会报错，只会让每次运行都悄悄改产品数据。
