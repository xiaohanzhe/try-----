### 为什么上轮只敢标"可选"、这次却好做（重要）
上轮担心"UI 打字机要改成追加模式"。摸清后发现**结构本来就不用改**：
打字机 = `typing_text`（全文） + `typing_index`（进度） + QTimer 渲染 `typing_text[:index]`。
**只要让 `typing_text` 可追加**，`typing_index` 留在原位，定时器下一拍自然继续往新内容上打 →

### 三个必须守住的决策（都有回归锁）
1. **基类 `chat_stream` 是具体方法、不是 abstractmethod**（默认=回落 `chat()` + 单分片回调）——
   否则 `LocalAIStub` 与用户 `register_provider()` 的实现被迫改造，App 一升级就崩在用户那边。锁 A1/A2。
2. **流式显示只做"前缀安全"清洗**（剥 markdown / 截自问自答），判退与超长截断留给收尾 `_clean_ai_reply`。
   两条规则**共用同一份定义**（`_md_strip_re()` / `_role_marker_re()`），否则规则漂移=字打出去又被改掉。
   一句话：**流式负责"看着像人话"，护栏负责"最终算数"**。锁 C1/C2/C9/C11。
3. **流式与"判退重采样"天然冲突**：判退发生在收完之后，可被判退的半句**已经在屏幕上**。
   所以重采样前必须先发 `None` 分片让 UI 擦干净（`_stream_reset()` 回「……」），否则新句粘在旧句后面。

### 新增教训（本轮）
10. **`requests.iter_lines()` 默认按 512 字节攒批**，会把流式的首字收益吃掉近一半（0.45s vs 0.23s）。
   要低延迟必须 `chunk_size=1`。
11. **`func_src` 式"首个 `def X(` 匹配"会取错函数**：①`def chat(` 会命中基类的抽象方法而不是子类实现；
   ②`def __init__` 会命中文件里第一个类的（DialogueUI 的 `__init__` 只有 7 行，打字机状态其实在
   `_init_state()` 里）。定位真实方法要**先切类段再找**，或直接断言整文件唯一 needle。
12. **needle 里含字符串字面量 → 用 `code_no_comment`；要排除 docstring 干扰 → 用 `code_only_src`**。
   两个工具各有用处，本轮两种错法各踩一次（B8 用错丢字面量、B9 需要用错会误命中 docstring）。
13. **断言必须带上中间的 `try:`**：`code_only_src` 把缩进全抹平，`ifnotstreamed:self._ai_thinking_off()`
   匹配不上实际代码（中间隔着 `try:`）→ 写成 `ifnotstreamed:try:self._ai_thinking_off()`。
14. **流式清洗不可能对所有文本前缀单调**：`1. `（要等点号后的空白）与 `主人：`（要等冒号）都是
   "需要看到后面字符才能判定"的规则，所以被延后剥掉的 1~2 字符**必然已经显示出去**。
   不要试图靠改规则消除它 —— 试过"提前剥"，会把开头的 `1.5 倍` 误伤成 `5 倍`，更糟。
   正解是**调用方检测"新结果不是已显示内容的前缀"就整段替换**（最终态一定正确）。
15. **Qt 跨线程投递必须单独验**：A~D 组只测到"函数级别"，而分片是*工作线程 emit → 主线程槽执行*；
   这条链路接不上，流式就**一个字都不显示**。用 `QObject` + 真 `pyqtSignal` + `processEvents()`
   起最小宿主，断言"按序投递 + 丢弃过期世代 + reset 顺序严格保持"。锁 F1/F2。

## 第五轮（同日深夜，收尾）：S7 lean 修复 + 7B 结案 + 提交推送

开头是上一轮留下的 S7 收尾（提交推送 + 报告 + 记忆），但**真机 e2e 抓出一个"不修就等于没做"的问题**，
于是本轮实际做成了三件事。

### 一、lean 请求：S7 第一批迁移本来是"白做"的

`speak_event` 第一版（流式 + 1200ms 首字兜底）上真机后**从来没走成过 AI**：

```
(b) AI 开：气泡 = [('罐头兜底句', False)]   ← 永远罐头
    ★App 链路首字 = 3.02s（纯链路 P1 中位 0.88s；时限 1200ms → 超时）
(c) 稳态复测：2.53s → 同样超时
```

**三次猜错才找到真因**：
1. 猜"system 太长" → 对照实验否掉（23 字 vs 1723 字，首字 226ms vs 266ms，纹丝不动）；
2. 猜"冷加载" → P1 已经预热过，否掉；
3. 第三次做**正确的对照实验**（`probe_prefix_cache.py`）→ 钉死：

| 用例 | 首字中位 | 相对 A |
|---|---|---|
| A 稳定 system（persona） | **628 ms** | — |
| B persona + 146 字**每轮都变**的尾部 | **1815 ms** | **+1187 ms（2.89×）** |
| C 稳定 system + 每轮都变的 history | **1148 ms** | **+519 ms** |

→ **机制：Ollama 的 KV 前缀缓存只复用"从头逐字相同"的那一段。**
system 尾部一变，那 ~100 token 就要重算，而本机**未命中缓存的 prefill 只有 40~100 tok/s**
（CPU-only，无独显）→ +1.2s；history 再 +0.5s。**"变化的部分放在哪里"才是主因，"总长度"不是。**

**修法**：`chat_with_ai(..., lean=False)` 新增形参；`speak_event` 是唯一传 `lean=True` 的调用点 ——
不发 history、不发【此刻】/话题锚/记忆召回（且 lean 下**不调用** `recall_text`）。
**对话路径一个字节没改。**

**实测效果**：App 链路首字 **3.02s → 0.91s**（稳态 **0.83s**）→ **真的走 AI**；
实发请求从 `system 1825 字 / history 2 条` 变成 `system 1591 字 / history 0 条`；
整句 3.31s/3.17s → 2.09s/1.33s。
