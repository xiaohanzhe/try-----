### ★★ 核心结论：失真不是"模型不行"，是**提示词给了可逐字搬走的模板**

这是本轮最值钱的一句。真机取证（8 场景 × 3 次 = 24 条真实回复）：

```
开头复读 15/24 = 62%；任意位置复读 21/24 = 88%
开头复读分布（去重）：嗯——×5、唔……×4、是这样啊……×3、诶！真的吗？×3
```

**只有 4 个起手式覆盖全部 15 次命中** → 用户说的"失真"就是这个：
不是某句说错，而是**每条回复都从同一句起跳**。

根因：persona「碎片」区是**按场合分组 + 冒号 + 固定例句**
（「坏消息的时候用：是这样啊……／那……现在还好吗／…」）——
**"分组 + 冒号 + 例句"这个格式本身就在教模型"这个场合该说这句"。**

### A/B 对照（唯一变量 = 这一段写法）

`probe_ab_fragment.py`，同模型/同温度/同场景，**先断言 A ≠ B**：
  **A 现状 61% → B 拟改 28%**

★ **但 B 组剩的 28% 里 `诶！真的吗？×4` 仍占大头** ——
因为我在 B 里**还留了一句**「诶！真的吗？」当说明性例子。
**⇒ 只要那串字还在 persona 里，4B 就会搬。正式版一个例句都不留。**

改法：例句 → **情形描述**（`· 一急、一慌 → 重复同一个字`），
并把"每次现造"从暗示提升成**显式硬要求**（"第一句话的开头必须针对他刚说的那句现写，
不要固定用同一个字起头；连着两次都是'一时不知道说什么'，两次的开头也得长得不一样"）。

### 失真②：括号旁白有洞（`strip_action_parentheticals`）

只匹配**动作词开头**的括号；`（心里有点慌，怕自己做得不好）` 这类
**描述性旁白**全漏（实测 5 种形态）。`looks_like_narration` 只看**整句首字符**，
括号在句中根本不看。

★★ **本轮先做错了一版，回归锁当场抓出来（这是锁在正确工作）**：
第一版用**窄白名单**（只放过 `其实/……` 开头），结果**把合法心里话一起误杀** ——
C19 / A22c 报红：`（我想想该怎么说）`/`（抱歉，我不是故意的）`/`（笑不出来）`/
`（因为……我一直都是一个人）` 全被清掉。
**误杀 = 该说的话被吞掉，比漏过更糟**（项目里反复出现的取舍）。

修正：**改抓"形态特征"而不是"首词白名单"** ——
`_NARRATION_INNER` 匹配"从外部描述自己"的固定开头（`心里/语气/神情/沉默/愣了/…`）→ 清掉；
第一人称的话语（`其实…/因为…/抱歉…/我想想…`）→ **原样保留**。
判据从"只放过谁"翻成"抓谁"，这是本轮的方法收获。

### 失真③：伪造"俩人共同经历"

真实回复出现「**我们那时候总坐在石阶上**，谁也不说话」——用户从没去过黑暗世界。
persona 只说"可以当闲话提"，**没禁止**讲成共同经历 → 4B 把"我自己的过去"
写成了"我们的回忆"。**这是在编造用户的人生**，比语气问题严重。

改法：明令「屏幕对面这个人没有去过黑暗世界，那些事他都不在场…只能说成我自己的过去，
不能编成我们俩一起经历过」。验收：**编造共同经历 0 处**。

### 路由层设计（本轮核心交付）

**路由是数据，不是代码** —— 规则全在 `_routes.json`，`scene_routing.py` 只做「读 + 匹配」。

- 分层：**语境 → `match()`（纯函数）→ route `{to,reason,priority}` → `follow_route()` → `switch(scene_id)`**
- **匹配语义**：`when_scene/area/chapter` 相等 + `"*"` 通配；`when_mood/event` 单值或数组（命中任一）；
  `when_keywords` **OR 语义**（与其余键的 AND 语义**刻意不同**）；
  排序 = `priority` 升序 → **命中条件数降序** → 声明序（稳定排序）
- **三条设计律**（全部配正/负控制成对）：
  1. 匹配不到返回 **`None`，绝不伪造一条默认路线**（`None` = 「没有任何理由换场景」→ 原地不动）
  2. **坏规则跳过，不作废整张表**
  3. **未知条件键一律放行**（渐进增强）
  ★ 方向刻意选的：**放行的风险"能被观测到"，拒绝的风险是"静默失效"**
- ★ **`_as_set()` 的坑**：`set("abc")` → `{'a','b','c'}` ⇒ 字符串一律当**单个值**
  （否则 `when_mood: "happy"` 会静默匹配上 `'h'`）
- ★★ **零行为变化**：路由层**没有自动调用方** —— 不注册定时器、不挂事件链路、不自己播动画、
  **只有 `follow_route` 允许调 `switch`**（锁 H1–H5，含负控制）
- ★ **`destinations()` 过滤未登记场景**（拿 `_index.json` 过滤）→ 防 AI 被送往
  「路由表写了但场景不存在」的地方（那会 `switch()` 失败，表现为「**走了一半停住**」，很难查）
- ★ **零依赖纪律**：`scene_routing.py` **禁 Qt、禁项目内业务模块**，只准标准库 + `scene_system`
  （`main.py` 在 **import 期**就 import `scene_controller`，回头 import 有反向依赖的模块会**把环接上**，已踩 4 次）
- ★★ **状态预声明铁律**：控制器会用到的字段**必须在宿主 `init_systems()` 预声明**
  （否则 `__setattr__` 判据不满足 → 状态劈两份，**G2 完全看不见**）。本轮 +3：
  `_scene_routes` / `_routes_loaded` / `_scene_route_reason`

### ★★★ 本段最重大发现：4B 产品链路首字是 36.8s，不是 0.6s

第 29 轮我报"4B 首字 0.6~0.7s 合格"——那是**裸测**（短 system，21 token）。

|---|---|---|---|---|
| 短 system | 21 | **0.33s** | 10.2 | 3.92s |
| persona（冷） | 2322 | **36.82s** | 8.4 | 2.63s |
| persona + 3 轮历史 | 2363 | **1.91s** | 8.3 | 2.54s |

★ **同一 prompt 长度差 19 倍**（36.82s vs 1.91s）⇒ 我第 29 轮的简化结论
「**决定首字的是 prompt 长度**」**被推翻** —— 真正的变量是「**KV 缓存是否命中**」。

**★ 教训（已进 MEMORY.md §5）：测性能必须用产品真实输入。**

### ★★★ 因果定位：「变化段位置」决定缓存能复用多长（29 倍）

第一次 A/B（`cache_position_ab.py`）**设计有缺陷**：4 次调用每次 system 都不同
→ 没有一次真正命中缓存 → 跑 13 分钟全是冷启动，结论行 `倍数 = 1.0×` **无意义**。
**如实记录这个失败**，重做 v2（`cache_position_ab2.py`）：**先喂热前缀，再只改一个变化段**。

| 变化段位置 | 改一次的代价 |
|---|---|
| **靠前**（persona 之后紧跟【此刻】） | **73.44s** |
| **末尾**（【此刻】挪到 system 最尾） | **2.50s** |
| | **倍数 = 29.4×** |

同一变化量、同一 prompt 长度（3629 token），**仅位置不同 → 首字差 29 倍**。

★ **机制**：Ollama（llama.cpp）只复用「**从 prompt 开头起、逐字相同**」的最长前缀。
变化段落在哪，缓存就从那断 ⇒ 后面所有 token 全部重算（prefill 是 decode 的约 10 倍慢）。
★ 对照：产品里 `persona`（**每次逐字不变**）是唯一稳定前缀 ⇒ **它越长，缓存越值钱**。

### 产品已有这套设计（本轮只是量化了它）

- `lean`（事件台词）**只发 persona，一个字节都不变** → 注释记「首字回到 0.6s 量级」；
- 世界观**从常驻 system 前缀改成按需召回**（`~4380 → ~2800` token），
  理由明写「**保 KV 前缀缓存** —— 它一抽掉，骨架前缀更短且更稳」；
- **关系 brief 刻意排在所有临时状态之前**，注释：「关系比这些变化得慢得多，
  放在前缀更靠前的位置，跨轮更容易保持逐字相同，**KV 缓存复用得更长**」；
- 每轮必变的三段（`_build_ai_context` / `focus` / `recall`）**全部追加在 system 末尾**。

⇒ **产品组装顺序已经是位置最优的**。本轮实测正好**印证并量化**了第 20 轮的设计正确性。

根因：`TimedRotatingFileHandler.doRollover()` 由 `emit()` 内部调用（**每次写日志都可能触发**），

`logger_utils` 的 try/except **只包住构造，包不住运行期 rollover**。
后果：**日志永不切割**（`backupCount=7` 形同虚设）+ 反复刷 Traceback。

⇒ **方法论增量：「静态审查找结构问题，真机跑才能找环境相关缺陷」**。

### ★★ F5 复验的反转：换了一个错，且是另一个 handler

```
File "C:\Python311\Lib\logging\__init__.py", line 1114, in emit
    self.flush()
File "C:\Python311\Lib\logging\__init__.py", line 1094, in flush
    self.stream.flush()
OSError: [Errno 22] Invalid argument
```

**这是 `logging.StreamHandler.flush()`（控制台 handler），不是 FileHandler。**
⇒ 判定为**探针假象**：我用 `stdout=open(log)` 把子进程 stdout 重定向到一个
Python 文件对象，该 handle 的 `flush()` 在父进程侧不稳定。

### ★★ F7：本轮最重发现（`_index_of_floor` 返回 -1 不是安全哨兵）
