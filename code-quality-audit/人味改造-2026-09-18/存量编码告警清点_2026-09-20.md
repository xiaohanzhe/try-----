## 1. 确定性损坏（3 个，`rc=1` 的直接来源）

| 文件 | 症状 | 可恢复？ |

| `人味改造-2026-09-18/_evidence/G2_回归_24套件_1135PASS_2026-09-19.txt` | 1723 × U+FFFD（`EF BF BD` 连排） | ❌ **不可恢复**（字节已丢） |

| `第六轮/_evidence/_diff_numstat.txt` | `FF FE` = **UTF-16 LE BOM**；内容纯 ASCII | ✅ **无损可修** |

### 1.1 已处置：`_diff_numstat.txt`（本类里唯一安全的一个）
它**不是损坏**——是一个合法的 UTF-16 文件，被"只认 UTF-8"的校验器误报为"不是合法 UTF-8"。
内容逐字符可解（`2\t2\tralsei_pet/config.json` … `633\t947\tralsei_pet/src/main.py`）。
- 做法：`bytes.decode('utf-16').encode('utf-8')`（**逐字符不变**），原字节先备份到
  `E:\Download\_tmp\_diff_numstat.utf16.bak`（364 B）再就地重写。
- 复核：新文件 `50 9 50 9 114 97 108 115`（`2\t2\tral`），`fffd=0`、无 BOM、
  `decode('utf-8') == 原文` → **内容零损失**。

### 1.2 待拍板：2 个 U+FFFD 文件（**不可恢复**）
- **成因**：早期用 `& py x.py *> o.txt` 捕获原生 stdout → PowerShell 按 GBK **有损**解码再按 UTF-8
  重写 → 原始字节**永久丢失**（GBK 编不回原字节，往返判据永不触发，这就是当年翻车的经典坑）。
- **现状**：这两个文件仍被**报道与记忆引用**：
  - `.workbuddy/memory/2026-09-19.md:433`
  - `.workbuddy/memory/参考-契约与历轮（详版）.md:403`
  - 且二者**都被 git 跟踪**（不能删）。
- **三个可选项**（择一，见 §3 待决策）。

## 2. 告警（75 个）—— 建议冻结归档，理由如下

### 2.1 分布：全部集中在编码纪律建立**之前**
| 轮次 | 数量 | 时间 |
|---|---|---|
| 第八轮 | 27 | ~09-14 |
| 第六轮 | 14 | ~09-14 |
| 第五轮 | 14 | ~09-13 |
| 第九轮 | 11 | ~09-15 |
| 人味改造-2026-09-18 | 6 | 09-18 |
| 架构改造-H4H5 | 5 | 09-16 |
| 人味诊断-2026-09-18 | 1 | 09-18 |

`75 个带 BOM`，其中 `32 个兼有"疑似乱码"绊线命中`。

### 2.2 抽验：乱码是**真的**，但**结构完好**
以 `第六轮/_evidence/final_regress.txt` 为例：
```
=== round6 ===
=== A. 鍐呯疆鍙拌瘝锛堢郴缁熻嚜甯﹀璇濓級宸插垹闄?===      ← 中文标签真乱码
  [PASS] A1 RalseiPet 涓?20 涓唴缃彴璇?鍋囨惉杩愭柟娉曞叏閮ㄤ笉瀛樺湪 :: still present=[]   ← 结论可读
```
**ASCII（`[PASS]` / 方法名 / 计数 / 断言结论）全部完好**，只有中文描述糊了。
→ 这些文件**仍具备"当时跑过、结果是 X"的证据效力**，只是不适合当阅读材料。

### 2.3 为什么不逐个修
1. **改了就成假证据**：重写中文标签 = 用我今天的文字替换当时的输出，**不是原件**。
2. **BOM 修起来便宜但没收益**：75 个逐个去 BOM 是纯机械动作，收益仅是校验器变绿；
   代价是**75 次对跟踪文件的写入 + 75 条 diff 噪音**，且历史证据的可信度不升反降。
3. **正确姿势是新旧分离**：纪律已建立（让 Python 自己写 UTF-8），**新证据已是 0 告警**；
   旧的按"历史归档"冻结即可。

## 4. 附：本轮对校验器的一条改进建议（未做，待批）

现状：校验器把"合法 UTF-16（带 FF FE / FE FF BOM）"判成"不是合法 UTF-8 → 确定性损坏"。
这与事实不符（UTF-16 内容并未损坏）。
- **建议**：识别 UTF-16/UTF-32 BOM → 单独归类为「**非 UTF-8 编码（内容可无损转换）**」，
  仍计告警但**不计入"确定性损坏"**，并在消息里给出"可无损转 UTF-8"的提示。
- 依据：本轮 `_diff_numstat.txt` 正是被这条误判打进了 `rc=1` 的"必须修"档，
  而它其实是三个里唯一内容完好的。
- **若采纳，则确定性损坏从 3 → 2**（且这 2 个是真丢字节，名副其实）。
