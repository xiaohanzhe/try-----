# 第二十二轮报告 · 回答篇幅约束（2026-09-20）

> 用户口径：上一轮末尾我提出"问设定类回答偏长"，用户回复 **「那就加」**。
> 本轮只做这一件事：把"追忆/复述往事类回答要短"变成**可执行、可回归**的约束。
> **不动召回逻辑**（网图、MAX_BLOCKS、触发词一律未改）。

旧上限 150 让 **10/12** 条正常回答被砍掉尾巴，而用户要的是"短一点"，不是"砍一半"。

## 1. 为什么"加一条口径"不够（两层一起改）

只改 persona 有两个问题：

1. **提示词不是保证。** 本项目已经反复证明（3B 时代实测连着吐客服腔、
   `_evidence/probe_vividness.txt`），模型写在 persona 里的禁令**会被违反**。
   篇幅这种事若只靠"叮嘱"，就是又一次把产品行为押在模型的自觉上。
2. **代码层本来有一道闸，但它是坏的。** `_clean_ai_reply` 第 3 步早就在做超长截断，
   只是阈值 `AI_REPLY_MAX_CHARS = 150` **低于模型的正常输出长度**（见 §2）。

所以本轮做成**两层**：persona 负责"让他自己想短"，代码负责"短不过界"。
两者分工不同 —— persona 管**倾向**，闸门管**兜底**。

---

## 2. 核心发现：旧上限 150 根本没在管对话

### 2.1 数值来源失准（换底座没跟着改）

- `AI_REPLY_MAX_CHARS = 150` 是 **3B 时代**定下的（那时 `num_predict` 更小）；
- 换成 4B 后 `ralsei.modelfile` 是 `PARAMETER num_predict 256`，**上限没跟着复核**；
- 后果：4B 正常回答轻松越过 150 → **每一条都被截到 ~150 字**。

### 2.2 用实测数据重放两种阈值（可复算）

取本轮探针 12 题的**闸前长度**（模型原始倾向）：
`[330, 333, 329, 325, 86, 158, 154, 206, 153, 186, 178, 130]`

| 阈值 | 会截断 | 说明 |
|---|---|---|
| 旧 **150** | **10 / 12 条** | 绝大多数回答都被砍尾巴 |
| 新 **220** | **4 / 12 条** | 只砍真正偏长的那些 |

→ **6 条回答不再被白白砍掉尾巴。**
取证：`_evidence/reply_cap_2026-09-20.txt`

### 2.3 顺带更正上一轮的一个误读

上一轮我报告"开召回 214 字 / 关召回 129 字"，并据此说"召回让它变啰嗦"。
**那个 214 本身就是被 150 砍过之后的长度**，不是模型的真实倾向。
本轮拿到闸前真值：**开召回闸前均值 214 / 关召回 167** ——
召回确实让回答更长（+28%），但**远没有上一轮看起来那么悬殊**，
而且其中相当一部分是"召回块给了更多可说的事"这一**正常且期望**的效果。

## 3. 新值 220 是怎么算出来的（不是拍的）

```
num_predict = 256 token                        （ralsei.modelfile，硬事实）
×  1 token ≈ 1.36 个中文字                      （本轮实测，见下）
=  物理上限 ≈ 348 字                            （模型吐不出比这更长的）
取 220 = 348 的 63%，落在设计带 50%~75% 内
```

换算率**实测**方法：借 Ollama 自己的计数器（`/api/chat` 读回 `prompt_eval_count`），
三种体裁各测一条：

| 体裁 | 字符数 | token 数 | 字 / token |
|---|---|---|---|
| 口语闲聊 | 67 | 49 | 1.367 |
| 设定复述 | 120 | 89 | 1.348 |
| 追忆往事 | 117 | 86 | 1.360 |
| **平均** | | | **1.359** |

取证 `_evidence/token_ratio_2026-09-20.txt`，复算脚本 `measure_token_ratio.py`。

> 注意：`prompt_eval_count` 含对话模板的固定开销，分母被抬大 →
> 真实比率会**略高**，即这个估算是**偏保守**的（实际能吃下的字只多不少）。
>
> 我最初按经验估的是 1.42，实测 1.36 —— 差 4%，量级对但**不能当判据**。
> 所以 M2 锁的判据写成区间（1.30~1.60），既容得下重新测量的抖动，
> 又能抓住"真失准"（比如有人把 220 改成 400）。

## 4. persona 层：约束写在"规则区"，不是"碎片区"

改的是 `ralsei_pet/assets/ralsei_persona.md`，两处：

1. **「我怎么说」节**（规则区）新增：
   > 要说"那边"的事、或者我自己的事，也别一口气倒完 —— 挑最想说的那一两处讲，
   > 剩下的留到下次。越是熟的事越容易越说越多，最后变成在念一段说明。

2. **「我知道的世界」节**把原句收紧：
   > …像聊过去一样慢慢讲，而且一次只讲一小截，别一口气倒完，也别把话题硬拐过去。

### 为什么位置本身就是断言内容

persona 自己在结尾写死了喂法：

> 「先记三条…**这三条比下面那些碎片重要得多**」
> 「碎片只是调味，不是主菜」

把篇幅约束塞进**碎片区**，它就从"规则"降格成"示例" —— 而**碎片区全是短句**，
模型学的是那些短句的**样子**，约束本身反而被稀释。
所以 A12c 断的是**位置**（约束必须在碎片区之前），不是"字符串在不在"。
只断存在性，会被"随便塞哪儿"糊弄过去。

### 一处必须记的坑：我自己往 persona 里写了 markdown

第一版措辞用了 `**一次只讲一小截**`。这**直接违反 A11**（persona 是 prompt 不是文档，
出现 `**` 会被模型学去，实测输出过 `**听到也让我心里暖暖的**`）。
**是 A11 把我拦下来的** —— 这条锁的价值在于它防的是"我这种知道规则也会犯的错"。
已改为纯文本。

## 5. 代码层：`AI_REPLY_MAX_CHARS` 150 → 220

`ralsei_pet/src/main.py`，`_clean_ai_reply` 第 3 步用的那个常量。

改动很小，但**注释写了 20 行**，因为这里要防的是"下一次换底座又静默失准"：

- 说明原值为什么错（3B 时代遗留，换 4B 没复核）；
- 说明新值怎么算（num_predict × 实测换算率 × 0.63）；
- 写明**复核触发条件**：换底座 / 调 `num_predict` → 必须重跑
  `measure_token_ratio.py`，判据见 M2。

### 连带：C17 的恒真风险

C17 断的是"输出 ≤ 上限"。它的输入 `LONG_IN` 长度是固定的（~520 字）。
**若有人把上限调到超过 LONG_IN，C17 就退化成"输出 == 输入"的恒真断言。**
所以补了 **M5**：专门断"LONG_IN 确实超过上限"。
这是**给 C17 做的体检**，也是本项目"别把断言写在死代码上"的又一次应用。

## 6. 探针：真机行为级 + 一处保真度缺口

### 6.1 结果

| 组 | 结果 | 闸前均值 / 最长 | 闸后均值 / 最长 | 截断 |
|---|---|---|---|---|
| 开召回 | **12 PASS / 0 FAIL** | 214 / 333 | 165 / **220** | 4/12 |
| 对照（关召回） | **10 PASS / 2 FAIL** | 167 / 253 | 154 / 215 | 4/12 |

对照组的 2 个 FAIL 正是被召回救回来的题（托丽尔、Asgore）——
与上一轮结论一致，说明**召回确实在提供"他不知道就答不出"的事实**。

### 6.2 探针保真度缺口（本轮抓到的真问题）

改后的探针第一次跑出来，final 文本里赫然留着「（停顿了一下）」——
看起来像**产品漏删了动作旁白**。查下去发现是**探针的锅**：

- `modules/event_speech.py` 的 `_ACTION_VERBS` **含「停顿」**，正则能匹配，
  产品链路的 0a 步一定会删掉它（C18/C18b 锁着）；
- 而**上一版探针只复刻了长度闸，没复刻动作闸** → 报出了假问题。

差点据此去改一个本来正常的正则。已补齐 `_apply_gates()`（0a + 3 两步），
并把判据**从 `event_speech` 直接导入**，不另抄一份正则。

> 这条很值得记：**探针的"保真度"本身也要被质疑**。
> 它报出的每个异常，先问"产品真的会这样吗"，再问"是不是我没复刻全"。

### 6.3 探针还补了一份"篇幅观测"

在结果尾部新增闸前/闸后分布 + 截断清单，并明确标注：
> 探针只复刻与内容无关的两道闸（动作/长度）；第 1、2 步依赖会话历史，不在此覆盖
> —— 所以这里的"闸后"是**下界**，真实产品链路只会更短。

### 7.1 鉴别力体检（`check_discriminating_power_r22.py`）

每条新锁配专属破坏场景，确认"破坏了必红"：

| 锁 | 破坏场景 | 结果 |
|---|---|---|
| M1 | 上限改回 150 | 红 |
| M2 | 上限调到 400（超物理上限） | 红 |
| M2 | 上限压到 60（低于 50% 下限） | 红 |
| M3 | 上限设成 99999（不设防） | 红 |
| M5 | C17 输入被改短（C17 将恒真） | 红 |
| A12c | 篇幅约束移到碎片区之后 | 红 |
| A12c | 篇幅约束整条删除 | 红 |

### 7.2 体检脚本自己踩的三个坑（都是"夹具在说谎"）

这一步比锁本身更值得记 —— **体检脚本出的错，会伪装成"锁没鉴别力"**：

1. **破坏动作是空操作**：M5 第一次传的是 `main_src=MAIN`（未改动），
   等于没破坏 → 看到"M5 没红" → 差点误判成"这条锁没鉴别力"。
2. **没把锚清干净**：A12c 第一版只删了「我怎么说」那一处，
   但「我知道的世界」节里还有一处 `都别一口气倒完` → 锚仍在 → 假绿。
   **破坏必须清干净锚**，否则测的是"别处还有没有留着"。
3. **三元写反**（最隐蔽）：写文件的表达式写成
   `SUITE if <条件> else 原文件` —— 传了破坏版却写进**原版**，
   于是怎么都不红。**夹具把破坏吃掉了。** 已改成
   `suite_src if <条件> else 原文件`，并加断言"写入内容必须 == 传入内容"。

> 通则（与 MEMORY §5 同源）：**先怀疑夹具，再怀疑被测物**。
> 一个"破坏了也不红"的报告，第一种可能是锁没鉴别力，
> **第二种（更常见）是破坏根本没落到被测文件上**。
