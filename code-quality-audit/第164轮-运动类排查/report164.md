## 3. 逐段详录

### 3.1 段2 · 跳跃（核心）

**测法**：直接摆 `is_jumping / jump_start_time / jump_start_pos / jump_target_pos`，
逐帧调 `handle_jump(0.05, now)`，记录 `pos()` 相对起点的偏移。

**常量现场值**：`gravity = 500.0 px/s²`、`jump_duration = 1.00`、`jump_height = 50`。

| 用例 | 目标 (dx,dy) | x 范围 | y 峰值 | 落点 | 轨迹形状 |
|---|---|---|---|---|---|
| 原地跳 | (0, 0) | `[0,0]` | −63 | (+0,+0) | 先上后下 |
| 原地跳（短） | (0, 0), dur=0.4 | `[0,0]` | −16 | (+0,+0) | 先上后下 |
| 横跳 200 | (200, 0) | `[0,200]` | −63 | (+200,+0) | 先上后下 |
| 斜上跳 | (150, −80) | `[0,150]` | −109 | (+150,−80) | 先上后下 |
| 纯上跳 | (0, −60) | `[0,0]` | −96 | (+0,−60) | 先上后下 |

**原地跳逐帧（前 12 帧）**：

```
t=0.00 dx=+0 dy=+0     t=0.30 dx=+0 dy=-53
t=0.05 dx=+0 dy=-12    t=0.35 dx=+0 dy=-57
t=0.10 dx=+0 dy=-23    t=0.40 dx=+0 dy=-61
t=0.15 dx=+0 dy=-32    t=0.45 dx=+0 dy=-62
t=0.20 dx=+0 dy=-41    t=0.50 dx=+0 dy=-63   ← 顶点
t=0.25 dx=+0 dy=-47    t=0.55 dx=+0 dy=-62   ← 开始回落
```

**归因**：

- **垂直方向是对的**。`handle_jump` 用 `vy0 = (Δy − 0.5·g·T²)/T`（11524）。Δy=0、T=1.0 时
  `vy0 = −0.5×500×1 = −250`，`h_max = vy0²/(2g) = 62500/1000 = 62.5`，实测峰值 **−63**，吻合。
  ⚠️ 这条**第90轮已经修对**，本轮不要动它。
- **横向方向是错的**。11507 行 `vx = delta_x / self.jump_duration` —— 这是**定点匀速插值**：
  从起点按目标位移均分，跟"起跳速度"没有任何关系。所以：
  - `dx=0` 时 x 恒 0（看起来"正确"，其实是巧合，因为分子是 0）；
  - `dx=200` 时 x 在 1 秒内匀速扫过 0→200，**空中还能匀速平移**，违反"速度锁死"；
  - **只要目标有横向差，纵身一跳就会横移**，正是用户说的病根。

### 3.2 段3 · 坠落

**测法**：`start_falling()` 后逐帧 `handle_gravity_fall(0.05, now)`。

| 用例 | 帧数 | y 位移范围 | x 位移范围 |
|---|---|---|---|
| 静止坠落 | 7 | `+1 .. +32` | `+0 .. +0` |
| 带速坠落 | 7 | `+1 .. +32` | `+11 .. +70` |

**归因**：

- **水平惯性已经存在**（`fall_velocity_x = current_speed_x × 0.3` + 空气阻力衰减），带速时横向 70px，正常。
- **垂直位移被硬封顶**。`_fall_projection_px()`（287-302）：
  ```python
  levels = _landing_drop_height(pet, floor) / 5.0
  px = levels * FALL_PROJ_PX_PER_LEVEL        # 32 px/层
  return max(FALL_PROJ_MIN_PX, min(FALL_PROJ_MAX_PX, px))   # 32 .. 320
  ```
  即便 `handle_gravity_fall` 里 `fall_speed += gravity*dt` 累加出了真实下落距离，
  最终可用位移仍被压到 `[32, 320]`，且本例中 `levels` 算出来 ≤1 ⇒ 取**下限 32**。
  **屏幕上的观感就是"掉 32px 然后变扁"，不是抛物线。**

if getattr(self, '_cached_screen_geom', None) is not None:
    ...
    self.move(new_x, new_y)     # ← 整个 move 被这个守卫包住

`_cached_screen_geom` 只在 10446-10447 被赋值（每 3 秒一次）。探针**直接调 `_handle_mouse_follow`**，

| 负控制 | 光标放回中心 50px 内 | 10 帧位移 **(0,0)**（死区正常） |

## 4. 真缺陷清单

### D1 · 横向位移与初速度完全解耦（严重）

- **位置**：`main.py:11507` `vx = delta_x / self.jump_duration`
- **表现**：只要目标有横向差就横移，与"起跳时有多快"无关；空中还匀速平移（违反"速度锁死"）。
- **用户口径冲突**：「跳跃不能原地起跳后出现横向位移，你需要给他一个水平初速度他才能跳远，否则就是跳高」。
- **修法**：`vx0` 由起跳瞬间的 `current_speed_x` 给出并**锁定**；`x(t) = x0 + vx0·t`。

### ~~D2 · 坠落垂直位移被 32px 封顶（严重）~~ → **撤销（我判错了，第 ⑥ 步推翻）**

- **位置**：`main.py:250/311` `_landing_drop_height()` + `_fall_projection_px()`
- 原判定：「无论掉多高，屏幕位移恒 +32」「不是抛物线」。
- **撤销理由（用户 2026-11-05「你想一下 2.5D 游戏是不是这样的，是那就没错」）**：

  先看产品里高度 `z` 到底参与不参与绘制 —— `z` **只在起跳/坠落过程中**作为临时
  绘制偏移存在（`extra_z_height` 见 `handle_jump` 12209；坠落的 `_fall_projection_px`），
  **站定时不参与投影**。所以：**窗口的屏幕矩形 = 这块板子的平面位置**。

  于是在 2.5D 里一次"跳上窗口"的屏幕位移由两段组成：

  | 段 | 量 | 是什么 |
  |---|---|---|
  | 平面移动 | 大（几百 px） | 从地面那个点走到板子那个点（平面 1:1，不压缩） |
  | 抬高 | 32px/层 | 高度差在屏幕上的压缩投影（压缩比 ≈ 0.3） |

  而"掉下来"只发生第二段：平面不动，高度归零 ⇒ **落在板子正下方的地面**。
  屏幕位移就只有那 32px/层。

  ⇒ 这才是「偏俯视」的定义：**平面 1:1、高度压缩投影**。
  反过来才不对 —— 如果坠落也掉几百像素，等于"从板子上掉下来会瞬移回地面原来站的
  那一个点"，那不是 2.5D，那是"摔回存档点"。

  另外两点原判定也不成立：
  - 它**不是封顶**，是"这次该落到哪块平面"（`platform_height 差 / 5 × 32`）；
    第 6 层掉下来是 192px，不是 32px。只有"在桌面上被甩出去"（落差 0）才吃
    `FALL_PROJ_MIN_PX`。
  - **过程是加速的**：`handle_gravity_fall` 里 `fall_speed += g*dt` 再 `× dt`，
    只是距离短，所以看起来像"一下就到底"。
- **修法**：不需要修。见 §9.4 的完整推导。

### D3 · 不存在"助跑"这条路径（严重）

- **位置**：全局。`start_jump` 直接起跳，没有任何"速度不够就退回去再冲"的逻辑。
- **用户口径冲突**：「要有助跑距离哦」。
- **修法**：`motion2d.runup_distance(v_target, accel)` 反推后退距离，再由现有漫游驱动冲回来。

### D4 · 超限后**静默**放弃，不说话（中）

- **位置**：`_start_climb_transition`（11103）返回 `False` → 调用方兜底：
  上楼"保持原楼层"、下楼"服从重力"。
- **表现**：够不着的时候**没有任何反馈**，用户看不到"它试过但不行"。
- **用户口径冲突**：「无中途落脚那就**放弃或向用户求助**」。
- **修法**：走 `start_autonomous_speech` 说一句（不新增 UI）。
- **备注**：`_desktop_ground_y()` 取的是**任务栏顶边**（`wa.y()+wa.height()-height()`）。按"整张桌面是地面"的口径，这个函数的**语义要重新定义**（它是"避让任务栏"还是"地面"？）—— 归入第⑥步一并处理。

### D5 · `jump_height` 写了三处，**没有任何地方读它算位置**（轻，但属"注释说 A 实际是 B"）

| 行 | 动作 |
|---|---|
| 8342 | 初始化 `jump_height = 50` |
| 12664 | 动画结束后还原 |
| 17381 | `update_animation` 里设成 20（配 `jump_duration=0.5`） |

**全文件没有任何读取 `jump_height` 参与位置计算的地方。** 跳跃高度实际由 `vy0` 决定。
⇒ 改 `jump_height` 不会有任何效果（静默无效参数）。

### D6 · `_cached_screen_geom=None` 时跟随静默失效（隐患，非当前 bug）

- 10662 的守卫让 `move()` 整个被跳过；速度继续累加，位置不动，**无日志**。
- 正常流程 3 秒内会被赋值，所以现在不会发作；但初始化顺序一变就会"跟随失灵且查不出原因"。
- **修法**：为 None 时补一次赋值（或走 `_virtual_screen_rect()` 兜底），并打 debug 日志。

## 5. 需要用户裁定的两条

### R1 · 第十八轮"**勿回退**：不把跨层拆成逐层小跳"的前提，在 2.5D 下不成立

代码 11113-11125 明确写着"勿回退"。它的推理是：

> 宠物之所以被判到第 N 层，是因为位置落在**最前面**那块楼板的可见区域里，
> 而那正是"后面第 N-1、N-2 层被它挡住"的地方，**中间层在这个位置上没有可见区域**
> ⇒ 逐层第一步就吸附失败 ⇒ 永远上不去。

**这个推理成立的前提是"落点只能取当前位置的垂直投影附近"**（`_climb_probe_landing` 用 `cur` 做基准）。

但在 2.5D 口径下，正确做法是：**先在地面上走到中间层的正下方，再往上跳** —— 那时中间层
的可见区域就在头顶，`floor_visible_contains` 自然通过。**这正是"助跑"存在的意义**。

⇒ 也就是说，用户这次要的"分段"，正好解开了第十八轮卡死的那个结。
**但代码里写着"勿回退"，所以必须先经你确认才能动。**

**U1 · 楼层 rect 与虚拟屏的像素口径 —— 已定性：夹具环境问题，不判为产品缺陷**

  > · 裸进程（未建 `QApplication`）：`GetSystemMetrics(78/79)` 返回 **1707×1067**（逻辑像素）；
  > · 建过 `QApplication()` 之后：同一调用返回 **2560×1600**（正确）。

  **两者混用出现在夹具侧，不是产品侧**。
- **结论**：U1 撤销，不计入缺陷。
- **仍待真机确认的一点**（不影响本轮）：真机上 `desktop_floor` 走物理像素、宠物 `pos()` 走 Qt 逻辑像素，

### 9.1 ⑤-b 助跑：设计要点（都写进了代码注释）

**两个量严格分开**（用户原话：「这个预留点可别和助跑距离搞混了哦」）

| 量 | 值 | 由什么决定 | 谁负责 |
|---|---|---|---|
| **起跳点**（预留点） | 宠物**现在站的地方** | **空间**约束：要在目标边缘外留出腾空余量 | `_climb_landing` / 落点选择（本步**不动**） |
| **起跑点**（助跑距离） | 起跳点反方向退 `L` | **动力学**约束：`L = v²/(2a)`，速度差决定 | `_try_runup`（本步新增） |

**状态机**：`back`（退到起跑点，走）→ `dash`（冲向起跳点，冲刺）→ 到点后用**同一组参数**重放那次起跳。

**四条防坑（每条都有探针守着）**

1. **闸门分层**：不助跑 ⇒ 上限 = 走路速度（`max_speed/名义帧长` = 242px/s）；
   助跑 ⇒ 才允许提到 `RUNUP_SPEED_MAX` = 320px/s。
   实测 dx=272 的一跳：不助跑被拒（`too_far`），助跑后放行。
2. **不许假放行**：`_runup_ready` 只是"许可"，真正的上限取**助跑过程中跑出过的最高实测速度**。
   标了旗但只跑到 60px/s ⇒ 退回走路速度（探针 A 段）。
3. **冲刺必须压过距离减速**：`distance < 50` 那档会把目标速度压到 `speed*(distance/50)`，
   而到达阈值 30px ⇒ 起跳前最后几步正好落进这一档 ⇒ 实测速度掉到 1px/帧 ⇒ 闸门必拒。
   这是"助跑永远不成功"的头号陷阱，冲刺用 `max()` 顶在情绪/波动之后再盖过去（探针 C 段）。
4. **不许在 30px 外起跳**：通用到达阈值是 30px，差 30px 起跳等于把这一跳凭空拉长 30px，
   正好把助跑换来的速度吃掉 ⇒ 单独的 `RUNUP_FIRE_PX = 18`（探针 D 段）。

### 9.2 ⑤-b 过程中自己踩到并修掉的三个坑

1. **`desktop_floor['rect']` 在 `update_floors()` 之前是空 `QRect()`**
   ⇒ `floor_visible_contains` 恒 False ⇒ `_try_runup` 一律判"起跑点站不住"而放弃助跑。
   现象与"助跑根本没接线"**长得一模一样**。探针第一条判据就是靠它红的。
2. **速度换算用当帧 dt ⇒ 帧率放大**
   `speed` 的语义是**像素/帧**（位移全是 `速度 × 1`，不乘 dt）。某帧 dt≈2ms 时
   `5px/帧 ÷ 0.002s = 2500px/s`，闸门当场按 2500 放行 = **假放行**。
   实测探针打出 **2777px/s** 才暴露。改成统一用名义帧长（`_nominal_move_dt`）后，
   走路 151px/s、冲刺 310px/s，两者可比。探针 C 段加了一条 `≤ 1.35×` 的回归闸钉住它。
3. **`_start_climb_transition` 返回 False 会把刚排上的助跑当场作废**
   调用方拿到 False 就走进"下楼服从重力"兜底 —— 人还没跑起来就被扔下去。
   改成：闸门拒绝但**助跑已排上** ⇒ 返回 True（"已接手"），调用方不动 `current_floor`。

### 9.3 ⑤-b 第二半：分段（用户裁定「做，按 2.5D 解」）

**这一步推翻了第十八轮写死在代码里的「勿回退：不拆逐层小跳」**，所以单列一节留痕。

两边的推理摆在一起看：

| | 第十八轮的说法 | 本轮的说法 |
|---|---|---|
| 前提 | 落点只能取**当前位置的垂直投影**附近 | 落点由 `_climb_landing` 的 **90px 让开探针**吸附进目标层可见区域 |
| 推论 | 中间层在该位置没有可见区域 ⇒ 逐层第一步就吸附失败 ⇒ 永远上不去 | 从**落点侧**去问可见区域，中间层就能落 ⇒ 分段可行 |
| 结论 | 不拆 | 拆 |

⇒ 第十八轮的结论**只在自己那个前提下成立**，而那个前提本轮已经不成立了。
**不改**它原来担心的东西：`_climb_landing` / `_climb_probe_landing` / `CLIMB_LANDING_MAX_TRAVEL`
一个字没动，分段只是**换了一次目标**。

**实现**（`_segment_candidates` + `_try_segment`）

- 候选：`platform_height` **严格夹在**当前层与目标层之间，且**朝目标方向**（上楼只找更高、下楼只找更低 ——
  不这么限就会在两层之间来回弹），按"离当前层最近"排序（爬楼是一层层上，不是一次蹦到顶）。
- 一次只拆**一层**：站到中途板上以后，`check_nearby_windows` 那条既有链路会重新枚举候选，
  目标层仍在附近 ⇒ 自然再跳一次。**不在这里写死"要跳几段"**（那会变成第二个真源）。
- **预留空间**由 `CLIMB_HORIZONTAL_RUN = 90` 的让开探针实现（落点侧先水平推开 90px 再吸附 ⇒ 斜跳）。
  **不另加**起跳侧的预留 —— 两侧都留会叠成 180px，把本来够得着的一跳推成够不着。
- **递归闸** `_segment_busy`：`_try_segment → _start_floor_jump → _on_jump_rejected → _try_segment`
  会自己咬自己，没这道闸就是无限递归。
- **求助只喊一次**：分段内部那一跳失败时会再进 `_on_jump_rejected`，那时 `_segment_busy=True` ⇒ 不喊，
  由最外层统一喊（否则一次够不着会连说三句）。

**拒绝分派的最终顺序**（写在一处，别散开）：`too_far` → 助跑；助跑不行 / `too_high` → 分段；都没有 → 求助。

**验证**（`probe164_runup` F 段 11 条）：候选方向与排序 / 镜像下楼 / 无中间层 /
递归闸 / 真改成跳 5 层 / 候选全够不着时逐个试完再如实返回 False / 分段能接手时不喊 /
都不接手才喊 / 内层不喊。合计 **48/0**；全量 G2 **7348/0/162 全 IDENTICAL**。

### 9.4 ⑥ 坠落：细读 + 2.5D 推导后 **D2 撤销，不改代码**

原 §4 D2 写的是「坠落垂直位移被 32px **硬封顶** ⇒ 掉 32px 就变扁，不是抛物线」。
按 2.5D 口径重读后三处都要改口：

1. **它不是"封顶"，是"落到哪块平面"**
   `max_y = 起点 y + _fall_projection_px(落点楼层)`，而
   `_fall_projection_px = (platform_height 差 / 5) × 32`（每层 32px）。
   它回答"这次该往下走多少"，不是"最多只能走多少"。第 6 层掉下来是 **192px**，
   只有"在桌面上被甩出去"（落差 0）才吃 `FALL_PROJ_MIN_PX` 的 32。
2. **过程是加速的**：`handle_gravity_fall` 里 `fall_speed += g*dt` 再 `× dt`，
   确实是抛物线，只是距离短，看起来像"一下就到底"。
3. **"跳上去几百 px、掉下来 32px"不是缺陷，是 2.5D 的定义**：

   `z` 在产品里**只在起跳/坠落过程中**作为临时绘制偏移存在
   （跳跃的 `extra_z_height`、坠落的 `_fall_projection_px`），**站定时不参与投影**
   ⇒ **窗口的屏幕矩形就是这块板子的平面位置**。于是：

   | 动作 | 屏幕位移 = 平面移动 + 高度投影 | 说人话 |
   |---|---|---|
   | 跳上窗口 | 几百 px ＋ 32px/层 | 先"走"到板子那个平面位置，再抬高一层 |
   | 从板上掉下 | 0 ＋ 32px/层 | 平面不动，只掉高度 ⇒ **落在板子正下方的地面** |

   平面 1:1、高度压缩投影（≈0.3）—— 这正是「偏俯视」的数学定义。
   反过来才不对：若坠落也掉几百 px，等于"从板上掉下来会瞬移回地面原来站的那点"，
   那不是 2.5D，是"摔回存档点"。

⇒ **⑥ 不改代码。** 原 D2 的"严重"定级是我的误判，已在 §4 划掉并写明推翻理由。

#### (d) 产品侧顺带收紧一处（9 增 1 删）
