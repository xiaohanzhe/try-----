## 1. 这 42 条到底是什么

| 项 | 内容 |
|---|---|
| 条数 | 42（Horz 36 + Vert 6） |
| 章 | 全部 ch5 |
| 现状 `when_src` / `_original.via` | `obj_doorAny` ← **错的** |
| 真身（探针反查 `precreate -> obj`） | `obj_doorAnyHorz`(36) / `obj_doorAnyVert`(6) |
| priority | 7831 ~ 8057（散落在 7300~8097 里，42 个） |

三条**互相独立**的证据：

### ① 标错
这 42 条的 `_original.precreate`（`gml_RoomCC_<房>_<n>_PreCreate`）在第174轮那 51 条
变体取证里查得到，`obj` 字段是变体名。探针是**原作侧**的数据，不看产品表。

### ② 死边（关键）
`modules/item_interact.py` 的对象级匹配是：

```python
r.get('when_src') == src        # 精确字符串相等
```

而产品里这 42 扇门的 `src` 在**第174轮物化**时已经写成了变体名
（`obj_doorAnyHorz` / `obj_doorAnyVert`）。于是查询传进来的 `src` 永远是变体名，
而表里那 42 条的 `when_src` 是 `obj_doorAny` ⇒ **一条都匹配不上**。
⇒ 它们不是"将来会用上"，是**从来没有被消费过**。

### ③ 纯冗余
与第174轮落的 51 条在 `(场景, 目标, door_x, door_y)` 上 **42/42 完全重合**，未覆盖 0。

## 2. 为什么是"删"而不是"改标签"

改标签（`obj_doorAny` → `obj_doorAnyHorz/Vert`）看着更温和，实际更糟：

1. 改完它们就与第174轮那 51 条在 `(场景, 目标, 门坐标, src)` 上**完全重复**；
2. `_pick_by_pos` 的生效前提是"候选 >= 2 且**恰好命中 1 条**" ⇒ 每组两条候选 ⇒
   **挑不出唯一** ⇒ 走 fallback（priority 最小）；
3. priority 7831~8057 < 8100~8150 ⇒ 生效的会是**172 这批**。
   **结果一样，但"哪条在干活"从 174 变成了 172** —— 下一轮排查会按错的那条查；
4. 直接违反第170轮立的「**重复边不加**」。

⇒ 删。留档 `_evidence/removed176.json`（42 条原样对象），`check176 D 段` 验过可整段加回。

  **这条口径边界写在判据文案里**，不假装 42 扇都在验消歧。

## 6. 被撞的七套老锁（全部"引账"改口径，不是把数调小）

三套都是第170~174轮的历史分母写死了。改法一律是：**数值从留档推出来**，并加一条
"删掉的正好是那 42 条"的结构性断言。

### `check172`（8 红 → 33/33 全绿）
- 分母分**两套账**：`EXPECT_N = 798`（证据侧 `analyze172.json`，**冻结**）、
  `EXPECT_LIVE = 798 - len(REMOVED) = 756`（产品侧现存）。桥是 `REMOVED_PAIRS`。
- **A1**：priority 段位不再是"7300~8097 连续"，而是"空洞**恰好等于**留档那 42 个" ——
  洞多一个=误删，少一个=没删干净。
- **A5**：重复组从"5 + 变体覆盖组数（47）"改成结构性口径"5 历史 + 7 变体内部 = 12"，
  另加新不变式"**含 172 段边的重复组 0 个**"。
- **E1**：出口口径从"172 段的边"改成"**doorany 家族**的边" —— 有 16 个场景
  （ch5 的 cliffs / flower_castle / garden）**一条 172 段边都没了**，
  但出口由第174轮的变体边提供（同一扇原作门）。
- A5 的分母闸 242/425 → **227/409**（15 个场景原来是"172+174 双胞胎"凑出的 2 条候选，
  现只剩 1 条；16 个场景失去全部 172 段边）。

### `check173`（1 红 → 42/42 全绿）
- `EXPECT_ANY_EDGES = 798 - len(留档) = 756`、`EXPECT_ROUTES = 2768`，两个数都从留档推。

### `check174`（4 红 → 39/39 全绿）
- **B6**：172 段 `when_src == obj_doorAny` 现存 **756**（= 798 - 42），且没被改标签。
- **B7 语义翻转**：从"**留档 42 条，不修**"改成"现存误标 **0 条**，且留档那 42 条
  **逐条**探针反查都真是变体（没冤枉人、没夹私货）"。
- **C7**：旧表用 `现存 ∪ 留档` 还原（口径一字不改），另加"删边**没丢掉任何一个**
  `(源,目标)` 对"。
- **D0**：floor 2,810 → 2,768（= 2,759 + 51 - 42）。

### `check124 D2` / `check171 E1`（各 1 红 → 全绿）
- 重复行期望从"`5 + 变体边条数(=56)`"改成 **`5 + Σ(size-1) over 全变体族的重复组` = 14**。
  那 42 组原来是"172 + 174 双胞胎"，删掉 172 那条后只剩变体一条 ⇒ **不再是重复组**。
  按"变体边条数"算会得到 56（错），按"现状的重复组"算才是 14。

### 第36轮 `verify_scene_route_original C3a13`（1 红 → 60/60）
- `_n_any >= 798` → `>= 798 - len(留档)`。

### `check175 C5/C6`（2 红 → 37/37）—— ★ **原设计不成立**
- 这两条比的是 `git diff HEAD -- scenes/`，只有"第175轮还没提交"时才绿；
  一提交，`_routes.json` 变成唯一改动 ⇒ 恒红。**判据不能依赖"未提交状态"。**
- 改成**绑定到那次提交**：`git log -S original_room_id` 找到把 rid 加进去的 commit
  （`c42948a7`），再核它的 numstat —— 87 文件 / +87 / -0。同一件事，再提交多少次都不影响。

> ★ 这三套的改法本身是本轮的一条教训：**老锁的"历史冻结"不能靠"数字永不改"实现**，
> 要靠"数字有账可引"。留档 `removed176.json` 就是那本账。
