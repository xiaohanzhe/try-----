## 1. 这一轮要解决的真问题

第169轮收口时留下的那句「产品侧限制（记档，非缺陷）」：

> `route_for_door(sid, letter)` 每个 (场景, 门字母) 只返回**一个**目标，
> 而本轮有 **37 个场景**是一房多出口 ⇒ 运行时每场景只生效一条。

原作里同一间房可以摆**好几扇 W 门**，去向靠位置条件分流：

```gml
if (room == room_town_mid)
{
    if (x > 290 && x < 370)   { global.entrance = 20; room_goto(room_lw_icee_pizza); }
    if (x > 1730 && x < 1840) { global.entrance = 23; room_goto(room_alphysalley); }
}
```

而 `door_letter_of('obj_doorW')` 对这三扇门一律返回 `'W'` ⇒ 只按 (场景, 字母) 查，
**三扇门全去同一条规则**。用户在 `town_mid` 站任意一扇 W 门都进 `alphysalley`。

本轮做两件事：**把源码事实补进表里** + **让查找按门的实际坐标消歧**。

## 3. 本轮自己推翻的两个结论（价值有一半在这里）

### 3.1 `RE_GOTO.search()` 吞掉 `else` 分支（差点误删 10 条正确数据）

`diff170` 一开始报「表里有、GML 没有」**10 条**，形如 153 多出 156、156 多出 153 互为对方。
真因是我的解析器对每个子 `if` **只取第一个 goto**：

```gml
if (x > 600) {
    if (global.plot < 120) { room_goto(darkbulb_2); }
    else                   { room_goto(dining_a); }   ← 被吞
}
```

改成 `parse_block()` 递归 + 显式处理 `else`（条件记作 `!(cond)`）后，
`表里有、GML 没有` **10 → 0**，GML 分支 256 → **266**。
**那 10 条数据本来就是对的，是我的解析器缺了一层。**

### 3.2 `gml170` 没反转否定式 ⇒ 区间方向整个反了

修 `dw_city_big_1` 的坐标时看到：源码 `x < 10`，表里记成 `x_range = [10, None]`（即 `x > 10`）。
先怀疑是第169轮的错（确实有一部分是），但继续查发现**我自己也有一份**：

`else` 分支的条件我记作 `!(y > 4700)`，而 `axis_range_of()` 只解析里层 `y > 4700`
⇒ 解出 `[4700, None]`，语义却是 `y <= 4700`，**方向反了**。

被它污染 6 条：`!(y > 4700)` / `!(y < 200)` / `!(x > 1200)` / `!(x < 0)` 等。
而 `feasible170.in_range()` 正是拿这个 `lo/hi` 去算「命中哪扇门」——
**反的区间会把房间判错**，连带门坐标修正清单也跟着变：

| 指标 | 修前 | 修后 |
|---|---|---|
| `FULL`（能完整精确映射） | 20 | **23** |
| `BROKEN` | 19 | **16** |
| 门坐标修正条数 | 11 | **17** |

修法：`_unnest()` 把 `!(x < 0)` 翻成 `x >= 0`（`<`↔`>=`、`<=`↔`>`）；
**复合否定**（`!(x < 10 && global.plot < 120)`）归一不了 ⇒ 直接返回 `None`，
**不许拿否定范围内的一半条件当区间**。

### 4.1 为什么 12 条必须写 `door_y` 而不是 `door_x`

这几个房间里**两扇门的 x 完全相同**：

| 房间 | 门实例 |
|---|---|
| `dw_cyber_maze_rhythm` | (271, **1**) / (269, **2593**) —— x 只差 2px，y 差 2592 |
| `dw_cyber_musical_door` | (280, **0**) / (280, **460**) —— x **一模一样** |
| `dw_mansion_east_teacup` | (280, **4780**) / (280, **1516**) —— x 一模一样 |
| `dw_mansion_east_teacup_2` | (280, **4780**) / (280, **1356**) |

拿 `x` 去区分上下门会**判反**。所以这些规则一律写 `door_y` + `axis: "y"`。

### 4.3 ★ 重复边不加：9 条候选里剔掉 3 条

第一版落盘是 **9 条**（priority 7190~7198，总数 1,939），全量回归立刻炸出两处：

## 5. 产品侧：`route_for_door` 加一层消歧

`ralsei_pet/modules/item_interact.py`

```python
def route_for_door(routes, scene_id, letter, src=None, pos=None):
    ...
    # ③ 实例级消歧（第170轮）：只在"同场景同字母多候选 + 给了门坐标"时插一层
    got = _pick_by_pos(items, scene_id, _letter_ok, pos)
    if got:
        return got
    return _pick(_letter_ok)          # ← 老口径，逐字不变
```

`_pick_by_pos()` 三个前提**缺一不生效**：

1. 该 (场景, 字母) 有 **≥2** 条候选（只有一条时本来就不存在"走哪扇"）；
2. 给了这扇门的坐标；
3. 按坐标**恰好命中 1 条**。

命中 0 条（这扇门原作没给它单独规则）或 ≥2 条（两条规则记了同一坐标 ⇒ 原作那层条件我还没解出来）
**一律返回 `None`**，退回「priority 最小」。

`_rule_door_axis()` 的轴判定：优先 `_original.axis`，没有就按 `door_x` 推
（第168/169轮的规则没这个字段，但它们的 `door_x` 记的就是那扇门的真实 x）。
**必须 `isinstance(v, int)`** —— `0` 是合法坐标，用 `if v:` 会把 x=0 那扇门当成"没记"。

`build_props()` 改成 `route_for_door(routes, sid, letter, src=src, pos=o.get('pos'))`。

## 8. 教训

1. **★★★ 自己的解析器也要当成被测物。** 否定式不反转这个 bug 藏在 `axis_range_of` 里，
   表现却是"数据表方向反了"——如果我只改表、不查解析器，就会把正确的源码抄成错的。
2. **★★★ 判据的候选集必须和被测物同一套。** C2 假红 1,297 条就是因为我把候选限死在 W 规则里。
3. **★★ 变异测试预测错判据是常态，别把它记成失败。** 关键是"有没有红"，不是"红的是不是我以为那条"。
4. **★★ 单边条件的方向最容易写反。** `[None, 10]` 与 `[10, None]` 差一个 None 的位置，
   11 条就是这么错的；判据要把两种都算成"不同"再判方向。
5. **★★ 同房两扇门 x 相同时，只有 y 能区分。** `dw_cyber_musical_door` 的两扇门 x 都是 280。
6. **★★ 中文本地化名不能当键。** 老规则的 `src_room_name` 有"纸牌城堡·一层"这种，
   对账必须用 `src_room_id`。
7. **★ 元数据不消费 ≠ 可以不正确。** `entrance` / `x_range` 产品一行都不读，
   但它们是这一轮实例级消歧的判据来源，也是后人理解"这条规则对应哪扇门"的唯一线索。
8. **★★★ 重复边不加。** 与既有 `(when_scene, to)` 完全相同的边是**冗余**（同一个答案说两遍），
   补进去会让 `check124 D2` 判"同门重复"、把 `check169` 的覆盖桶从 `8/4` 挤成 `10/3`。
   第一版落了 9 条，全量回归炸出来才发现 ⇒ **应用器要有 `pair_exists` 闸**，
   不能只管"这条边能不能找到依据"。
9. **★★★ 判据不许绑轮次号。** `scene_route_original._table_self_ok()` 里写死
   `o.get('batch') == 169` 来判"这条规则是分支级还是字母级"，于是第170轮那 6 条
   （`batch == 170`）掉进"字母级"分支 ⇒ 被判不自洽 **7 条**。
   正确写法是按**字段存在性**判（有 `branch_letter` 就是分支级）。
   **判据里每出现一个具体轮次号，都是一颗定时炸弹。**
