> 日期：2026-11-03　｜　改动：`check138.py`（**+16 / −1，只动落盘段，判据一条没动**）· `phase138.json`（冻回 137/6120 + `_note`）
> 判据：`check144` **17/0** · `mutate144` **20/0**（8 处破坏）· `recheck144_core` **46/0** · 全量 **143 套件 / PASS=6671 / FAIL=0 / 143 行全 IDENTICAL**

## 0. 一句话

`check138.py` 每跑一次都往 `第138轮/_evidence/phase138.json` 写两个数
（`files_scanned` / `calls_scanned`），而这两个数**必然随套件数变化**。
六个提交连着改它，每次 **+1 个文件、+N 恰好等于那一轮新加的判据条数**。
⇒ 它不是"当时量到的东西"，是"套件清单长度的回声"。本轮把这份证据**冻在 138 轮那份**，
活计数外移到 `.gitignore` 已整目录忽略的 `code-quality-audit/regress/_out/`。

## 1. 病：6 次纯机械漂移

`git log` 实证（`_evidence/lead144.json` 的 `history` / `deltas`）：

| 提交 | 轮次 | files | calls | 增量（对上一行） |
|---|---|---|---|---|
| `46288e2b` | 第138轮 | 137 | 6120 | —— |
| `43216d24` | 第139轮 | 138 | 6158 | **+1 / +38** |
| `ea67b36f` | 第140轮 | 139 | 6198 | **+1 / +40** |
| `c3600942` | 第141轮 | 140 | 6228 | **+1 / +30** |
| `5562ac09` | 第142轮 | 141 | 6246 | **+1 / +18** |
| `0e4544b3` | 第143轮 | 142 | 6274 | **+1 / +28** |

五个增量里 **每一行都是 +1 个文件**（`d_files` 集合 = `{1}`），
而 `+N` 逐条对上那五轮新加的判据条数（`check139` 38 / `check140` 40 /
`check141` 30 / `check142` 18 / `check143` 28）。

⇒ 这个文件里**没有任何"信息"**：给定套件清单，两个数就唯一确定了。
后果是每轮 commit 都捎带一个语义无关的改动，review 时纯噪声；
更糟的是**它是"证据"文件夹里的东西** —— 一个会自己变的历史证据，谁都不能拿它做对账。

## 2. 三条依据（改法之前必须先站得住）

1. **改过 6 次**且每次 `+1 文件 / +本轮判据数` ⇒ 纯机械漂移（§1 的表）。
2. **读盘 0 处** —— 全仓没有任何脚本读它。三处 `recheck1xx` 只是把它写在**工作区白名单**里
   （"已知刷脏、登记未修"），另有两处是 `check138` 自己的注释。
   ⇒ 停写的风险为零：没有人依赖它。
3. `code-quality-audit/regress/_out/` 已经在 `.gitignore` 里（整目录忽略）
   ⇒ 活计数有地方放，不必新造目录、不必动别的忽略规则。

## 3. 为什么不是"备份"，也不是"干脆不写"

- **备份被否**：`.gitignore` 里有 `*.backup*`。想给这个文件做跨目录备份，就得在仓库里
  再放一份 `.json.bak` 之类的东西 —— 那类名字要么被忽略（等于没进仓库），要么要新增
  忽略规则去救，而且**它治不了"每轮都改"**，只是把每轮都改的东西多存一份。
- **"干脆不写"被否**：这两个计数虽然会漂，但"当前扫描面有多大"确实还是有人想看的
  （它曾用来证明"全仓闸真的扫了 6000+ 处调用"）。删掉出口等于把测量能力一起删了。

⇒ 取中间那条：**证据冻结在仓库里，活计数留在工作区外。**
`_evidence/phase138.json` 冻在 138 轮那份（137 / 6120 / 0 / 0）+ 一段 `_note` 说明来历与替代去处；
`check138.py` 改写到 `regress/_out/phase138.live.json`。

## 5. 判据自身踩的三个坑（都写进代码注释）

### 5.1 `B2` 第一版读"运行产物" ⇒ 判据条数会随环境跳

第一版守的是「`_out/phase138.live.json` 与冻结文件**键集相同**」。问题：
那个文件在**新克隆的机器上不存在**，"有没有它"取决于**谁先跑过 `check138`** ⇒
`check144` 的判据条数会在 **16 / 17** 之间跳。
**"判据条数随环境变"本身就是缺陷**（基线立刻漂，而且漂的方式还很隐蔽）。

⇒ 改成**静态读源码**：AST 找出 `check138.py` 里 `_ev = {...}` 那个字典字面量的键，
和 `FROZEN_VALS` 的键对一遍。写什么，就看源码里写了什么 —— 确定的，
而且比"比对运行产物"更直接。`recheck144_core H4d` 现在专门钉这一条
（把 live 挪走再跑，条数必须一模一样：`有 live=17 / 无 live=17`）。

### 5.2 全仓扫描第一次直接崩在 `UnicodeDecodeError`

`os.walk` + `ast.parse` 扫全仓 `.py` 时崩了：
`'utf-8' codec can't decode byte 0xe6 in position 5`。
真凶是第113轮 `_tools/disk/` 下 **5 个非 UTF-8 脚本**，外加 `第五轮/_evidence/_scan_repr.py`
一个 `SyntaxError`（它是 repr 转储，不是代码）。

更要紧的是**修法不能是"静默 `continue`"**：那样"有一个文件根本没被扫到"
和"扫过且干净"输出一模一样 —— 这是本仓栽过多次的假绿形状。
⇒ 三件事一起做：

1. 被跳过的文件**逐个 `[SKIP]` 记名打印**（路径 + 异常类型）；
2. 对它们做一次**字节级**兜底（`B1c`）：`phase138.json` 若在文件里**一次都没出现过**，
   那它绝不可能写它 —— 这个方向是**单向证明**（不区分代码/注释只会误报，不会漏报）；
3. `B1b` 守扫描面不塌（可解析 `.py` ≥ 100 个）—— 否则 `B1` 会"全绿但什么都没看"。

### 5.3 ★ 我自己制造了一次 DIFF（第138轮那条口径，本轮又踩）

`check144` 首跑后被 `run_all` 判 **DIFF**，明细只有一行：

```
-[INFO] live 现值 {"files_scanned": 142, "calls_scanned": 6274, ...}
+[INFO] live 现值 {"files_scanned": 143, "calls_scanned": 6291, ...}
```

两个原因都是**我把时相量打进了输出**：
① `[INFO] live 现值 {...}` —— 那两个数每加一个套件就变；
② `[INFO] 扫到 N 个可解析 .py` / `B1b 实扫 N 个` —— 仓库每轮都会加脚本。

⇒ 三处全改：不打印 live 的值（连"在不在"都不打，它取决于谁先跑过 `check138`）、
不打印扫描面的大小（`B1b` 的 extra 改成固定的 `闸门=≥100`）。
**这正是第138轮那条口径**（判据的输出里不许含时相量），本轮由 `run_all` 替我抓了出来。

## 7. 连带登记：`merge_patches` 为什么不能"反正是重建"就放心

第139轮删掉 `patches["ralsei"]` 里那句重复之后留下的隐患：
`eval113.merge_patches` 在**只有旧键**时**保留旧补丁**，两边都有时走 `merge_text` **求并集**。

⇒ 重跑一次 `evaluate` 会让 `new` 里重新出现那句话，并集把它**带回来**
⇒ 「重建会把 ① 塞回 `ralsei`」是**条件成立的**（不是假想），
所以 `check139 A1`（"① 不在位"）**不能删**，而且哪天有人真跑了重建，它会先红。

`check144 C1~C4` 把这条链钉住：函数在 / 保留分支在 / 并集在 / 兜底判据在。
