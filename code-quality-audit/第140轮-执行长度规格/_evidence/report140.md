# 第140轮 · `length_policy` 从死数据变成真执行的规格（只执行字数那一半）

> 用户口径：「继续，按你的计划来就好」。
> 承接第139轮遗留 ②：「`length_policy` 是死数据（96 张卡写 `max_sentences: 3`，零读取）；
> 真要治'一次说几句'，正确落点是执行它，而不是再往 prompt 里塞一句话。」

---

## 1. 结论先行

四句话：

1. **`length_policy` 现在真的被执行了，但只执行 `max_chars`**（200，卡片驱动，只许**收紧**全局兜底 220）。以后调长度改卡片即可，不用动产品代码。
2. **`max_sentences` 明确不执行**，并且把它钉成了判据（`check140 E1~E4`），防止以后有人凭直觉悄悄接上。
3. **不执行的理由是数据，不是口味**：句数中位数 **4**、44.1% 的回复在 3 句以内；按 3 句砍要动 **55.9%**、按 6 句砍动 **15.1%**，而那批 6 句的回复平均才 150 字、本来就在字数预算内。
4. **顺手推翻了上一轮自己的一个数**：第139轮那个「>3 句 83.3%」是**切句口径的产物** —— 它把 `…` 当句号，而人设第 57 行写着「别拿它当句号」。

## 2. 病是什么：一张写了没人看的规格，和两套并存的数字

| | 值 | 谁在读 |
|---|---|---|
| `cards/<id>.json` 的 `length_policy.max_chars` | **200** | **零处** |
| `main.py` 的 `AI_REPLY_MAX_CHARS` | **220** | `_clean_ai_reply` 第 3 步 |
| `cards/<id>.json` 的 `length_policy.max_sentences` | **3** | **零处** |

96 张卡里 77 张写着 `{200, 3}`（另外 19 张是不说话的物件），全仓 `--include=*.py` 搜
`length_policy|max_sentences|max_chars` 在 `ralsei_pet/` 里命中 **0 处**。

⇒ 真正生效的是**没人维护**的那个 220。卡片写得再准，改它等于改了个寂寞。
这与第139轮清掉的那条"写了三遍"是同一个病：**规格存在，执行缺席**。

## 3. 先量再改：第一件事是把尺子校准

第139轮我量过"7B 有多少条不遵守 3 句"，得出 **40/48 = 83.3%**。
本轮一上手就撞到问题：那个切句器把 `…` 当句末标点，而人设第 57 行白纸黑字写着

> 句子说一半停住、用省略号让声音软下来：**很少用，别拿它当句号**。

**拿一条人设明确否定的口径，去判人设的遵守率** —— 尺子本身就是被测物。

同一批 48 轮，三种切法（`_evidence/length140.json` 的 `splitters_raw30`）：

| 切句口径 | >3 句 | 占比 |
|---|---|---|
| A 含 `…`（= 第139轮） | 40/48 | **83.3%** |
| B 不含 `…`（人设口径） | 31/48 | **64.6%** |
| C 不含 `…` 且引号内不切 | 24/48 | **50.0%** |

83.3% 这个数**可复现**（A 口径逐字复刻），但它量的是"带省略号的口语里有多少个标点"，
不是"说了几句"。

★ 顺带说明为什么产品代码里 `_SENTENCE_ENDS` **是**含 `…` 的：那是为了"截断切点要温柔"
（切在省略号后比切在句号上更软），和"数句子"是两件事。**同一个项目里，两个用途要两套标点集**，
这不是重复定义，是分工 —— 本条写进了 `check140` 的注释，免得下次有人"统一"掉。

## 5. 天花板该定在哪：扫描 + 一个被数据否掉的方案

| 天花板 | 会截的条数 | 占比 |
|---|---|---|
| 3 | 3127 | **55.9%** |
| 4 | 2147 | 38.4% |
| 5 | 1380 | 24.7% |
| 6 | 842 | **15.1%** |
| 8 | 256 | 4.6% |
| 10 | 72 | 1.3% |

我最初的计划是"按 `max_sentences` 加一道句数上限"。数据把这个方案否了，三条理由：

1. **按 3 句砍 = 动一半以上的回复**。这不是"抓跑飞"，是"重写行为"。
2. **按 6 句砍也要动 15.1%**，而那批 6 句的回复**平均 150 字**，本来就在字数预算内
   —— 说明"句子多"和"话太多"不是同一件事，句子数是个**抓不住目标的代理指标**。
3. **截断砍的是结尾**。人设要求的「先接住他那件事，再补一句我自己的感受」正好落在结尾 ——
   按 3 句砍，等于系统性地把"感受"那半句削掉。**这比话长更伤人。**

⇒ 唯一诚实的做法：`max_chars` 执行（它真的就是截断阈值），`max_sentences` **读进来不用**，
并把"不用"写死成判据。

## 6. 改了什么

### 6.1 加载层（`modules/npc_persona.py`，纯函数、零依赖、零 Qt）

```python
def training_length_policy(npc_id, assets_dir=None):
    """→ (max_chars, max_sentences) 或 None"""
    # 读 cards/<id>.json 的 length_policy
    # 校验：type(x) is int 且 > 0 —— 注意 isinstance(True, int) 是 True，
    #       用 isinstance 会把 "max_chars": true 当成 1，静默变成"每条都截到 1 个字"
def reply_length_limits(npc_id, hard):
    """→ 真正执行的 (max_chars, max_sentences)；卡片只许收紧 hard"""
    return min(card_chars, hard), card_sents
```

两处都带进程内缓存，读盘失败一律 `None` / 回落兜底（**不抛**），与 `training_patch` 同一口径。

### 6.2 执行点（`src/main.py`，只改第 3 步）

```python
max_chars, _max_sent = npc_persona_mod.reply_length_limits(
    speaker or 'ralsei',
    getattr(self, 'AI_REPLY_MAX_CHARS', None) or RalseiPet.AI_REPLY_MAX_CHARS)
if len(t) > max_chars:
    ...（原来的"从最近的句末标点截断"一字未动）
```

`_clean_ai_reply` 新增 `speaker=None` 第三参，`chat_with_ai` 的两个调用点把 `speaker` 传下去。
`AI_REPLY_MAX_CHARS` **仍是 220**（兜底不变，收紧交给卡片）。

### 6.3 数据：**一个字没改**

`cards/ralsei.json` 仍是 `{200, 3}`。本轮改的是"谁来读"，不是"值是多少"。

## 7. 踩到的坑（都是"看起来像产品坏了"的那种）

### 7.1 长度结算写成 `self._xxx()` ⇒ 整条护栏静默哑掉

第一版把结算写成了 `RalseiPet._reply_length_policy()` 方法。回归里有二十几个桩**只绑
`_clean_ai_reply` 一个方法** ⇒ 桩上 `AttributeError` ⇒ 被 `_clean_ai_reply` 自己的
`except Exception` **吞掉** ⇒ 走 `return reply` 分支 ⇒ **整条护栏返回原文不洗**。

症状：`persona_chat` 13 条 FAIL，全是"markdown 没剥""引号没剥""超长没截"，
看起来像我把护栏改废了。**这已经是本项目第三次栽在"桩上新增的链上函数"上。**

⇒ 改法：结算挪到**模块级** `npc_persona.reply_length_limits()`。桩只要 import 得到模块就成立。

### 7.2 循环变量用了 `_n`，把记账字典覆盖了

`for _n in ast.walk(...)` ⇒ `TypeError: 'Load' object is not subscriptable`。
本项目的 `_n = {'p': 0, 'f': 0}` 是记账口，**循环变量永远别叫 `_n`**。

### 7.3 变异脚本的锚点撞上 CRLF

`main.py` 工作区是 CRLF、`git show HEAD:` 里是 LF。直接拿 `'...\n'` 当锚点 `count()` 得 0，
报"锚点不唯一" —— 看着像判据问题，其实是夹具。已加 `_lf()` + `_eol_of()` 归一，写完按原 EOL 还原。

### 7.4 `[PASS]` 写进判据描述里，把 run_all 的计数顶高 1

`run_all.count_results` 是 `re.findall(r'\[PASS\]|\[\s*OK\s*\]', text)` —— 数**出现次数**。
我有一条判据的描述里带了 `[PASS]` 字样，于是 run_all 数出 41、套件自己数出 40。
差点当成"多了一条判据"提交。已改成 `'[' + 'PASS]'` 拼接。

### 7.5 两处过期的桩 / 注释（不是本轮引入，但被本轮照出来）

- `verify_s7_event_speech` 的 `fh._clean_ai_reply = lambda reply, recent=None: reply`
  不吃 `speaker=` ⇒ TypeError 被吞成一条 WARNING，污染输出比对。已补参。
- `event_speech.py` 注释写「对话链路是 `AI_REPLY_MAX_CHARS=80`」—— 实际早就 220。
  已改成不写死数字（写死的注释一定会过期）。

## 10. 遗留

1. **`max_sentences` 仍然是"读了不用"**。这是本轮**有意的结论**，不是没做完。
   真要治"一次说几句"，得先有一个能分辨"话多"与"句子碎"的指标 —— 句子数做不到。
   候选：单句长度、或"最长那一句占全文的比例"（念说明的形态是**一句很长**，不是句多）。
   **这条要做，得先量，不能拍。**
2. **字数上限只对**有卡的**角色生效**（77 张）。另外 19 张卡是不说话的物件，无需。
   若将来出现"某角色要说得更长"，改卡片即可 —— 但 `min()` 不许放宽兜底，这条是设计。
3. **本次改动对线上是 2.4% 的收紧**（5592 条里 `200~220` 字区间 135 条）。
   真机上"用户能不能感觉到"没测，只有离线语料。下轮真机复测时顺带看一眼。
4. **`_clean_ai_reply` 现在有三参**，凡新写的桩都得收 `speaker`。已在注释里写明，
   但这是"靠人记得"的约定，没有闸。
