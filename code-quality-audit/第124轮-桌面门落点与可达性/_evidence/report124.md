# 第124轮报告 —— 桌面 C 门落点写错：整个 UT 从桌面一间接不到

> 日期：2026-10-31
> 轮次目录：`code-quality-audit/第124轮-桌面门落点与可达性/`
> 新锁：`check124`（24 条）· 全量 G2：**PASS=6027 / FAIL=0 / 123 套件，全 IDENTICAL**

---

## 1. 一句话结论

桌面上的 **UT 门（C 门，正左）** 落点写的是 `ut.rooms.room_start` —— 而那是原作
**下标 0 的标题/空壳房**（一个门都没有）。所以玩家从桌面推门进 Undertale，
**进去只能站在那一间空屋子里，整个 UT 一间接不到**（实测可达 **1** 间）。

把它改成 `ut.rooms.room_area1`（原作下标 **4**，人类真正坠落的那片草地）之后：

| 指标 | 修前 | 修后 |
|---|---|---|
| 从桌面出发总可达 | 167 | **199** |
| UT 世界可达 | **1** | **33** |
| C 门目标的出边 | 0 | 1 |

改动量：**`_routes.json` 里 1 个字段**（`"to"`）+ 重写该条 `reason`。

## 2. 缺陷是什么

### 2.1 现象

`_routes.json` 桌面段 4 条路由（A~D），C 门指向 `ut.rooms.room_start`：

```json
{ "when_scene": "desktop", "when_door": "C", "to": "ut.rooms.room_start", ... }
```

`room_start` 在 ut 段路由表里**出边 0、入边 1**（入边就是桌面这一条）。
也就是说这扇门把玩家送进一个**没有任何门**的房间。

### 2.2 根因

**入口选错了一间房**，不是"路由条数不够"。
ut 段已有 **525** 条门路由（第122/123 轮补齐，门覆盖 1,233/1,299 = 94.9%），
但玩家根本走不到那些门后面去 —— 因为第一步就落在死胡同里。

### 2.3 证据链（三方独立）

| 出处 | 说了什么 |
|---|---|
| `第115轮/_tools/graph115.py` | 入口定义写明「入口 = `room_area1`，**不是** `room_start`」 |
| `第71轮/_tools/check71.py` D4 | 有一条判据专门问「落点写清了"为什么不是 room_start"」 |
| `第120轮/_tools/check_bg120.py` | `BLANK` 白名单里含 `room_start`（开场文字是对象自绘，房间本身空的） |
| 本轮实测（`第61轮/_evidence/ut_rooms.json`） | 0=room_start · 1=room_introstory · 2=room_introimage · 3=room_intromenu · **4=room_area1**（680×260） |

也就是说 **原作下标 0~3 全是开场/标题屏**，`room_start` 从来不是"坠落处"。

## 3. 为什么 122 套件一条都没抓到

这是本轮最值得记的一条：**所有锁都在看"表里有没有这条边"，没有一条看"人能不能走到"。**

- `check89.B3` 只验 `to` 能在索引里解析 → `room_start` **是**合法 scene_id，绿。
- `check89.B4` 只验覆盖三个世界（前缀 `ch1.` / `oneshot.` / `ut.`）→ 前缀对，绿。
- `check89.B4b` 验"字母 ↔ 目标逐条等于口径" → **但口径本身就是错的**，绿。
- `check89.B4c` 验"落点房间号 = 原作真值" → **期望值也写成 0**，绿。
- `check122` / `check123` 验 ut 段每条边逐条正确 → 它们不管"有没有人走到这里"，绿。
- 断链统计（`verify_routes_order44.C2`）把 `room_start` 记成"原作死胡同"→ 当成正常，绿。

⇒ **两条判据共享同一个错误假设时，互证不等于独立验证。**
`B4b`（落点 = `room_start`）与 `B4c`（期望下标 = 0）就是这么互相印证的。
本轮把 `B4c` 的期望值**纠正为 4** —— 这不是"为了让新值变绿而改判据"，
而是旧值**本来就写错了**（0 是标题屏）。

## 6. `check124` 守什么

| 段 | 内容 |
|---|---|
| **A 落点** | 4 条路由的 `to` 逐条等于口径 · C 门**不许**是 `room_start` · **每条目标的出边必须 > 0**（结构性判据，比字面量更根本）· 负控制：空壳房出边确实 0 · **落点真能画出来**（走产品 `load_scene` 拿到 `bg/ut_room_area1.png`，4,751 B）· 落点带 `obj_readable_flowers1` |
| **B 可达性账** | 桌面并集 ≥ 199 · 每扇门单独可达 > 1 · ut 从 `room_area1` ≥ 33 · **负控制：把 C 门换回 `room_start` ⇒ 总 167 / ut 1**（直接复现缺陷）· 守恒：可达 + 不可达 == 总场景（分母闸） |
| **C 空壳房负向锚** | 4 间空壳/标题房出边全 0 且**不在任何 `to` 里** · 负控制：`room_area1` 与它们相反 · **原作下标 0~3 恰好就是这 4 间**，`room_area1` = 4 |
| **D 密度账** | 每个作品"有出边场景数"只增不减 · 边数守恒 |
| **E 自检** | AST 数恒真判据（不扫注释）· 无 BOM / 无 U+FFFD · 被测文件在盘 |

**B4 是这套锁的核心**：它不读文件、不改盘，只在内存里把 C 门那一条换回
`room_start` 再重算闭包 —— 得到 167 / 1，与修前实测**逐值相同**。
这证明 `B1`/`B3` 抓得住"退回空壳房"这个回退。

## 7. 踩坑清单（本轮真踩到的）

1. **★★★ "判据互证"骗过了 6 轮**：`B4b` 把落点写成 `room_start`、
   `B4c` 把期望下标写成 0 —— 两条判据共享同一个错误假设，于是互相"印证"。
   **两条判据互证 ≠ 独立验证**。真值必须回到原作数据（`ut_rooms.json` 的 index↔name 表）。
2. **★★ 我自己写错了一条判据的假设**：`check124.C4` 第一版写"两间房
   `original_room_id` 都是 0"，实测是 **4 和 0**，当场报红。
   ⇒ **报红先怀疑判据**——这次报红是正确的，它抓出的是我的注释错误，不是产品错误。
3. **★★ 概念被我自己说错了**：`room_start` **有背景图**（`bg/ut_room_start.png`）。
   "空壳"的准确含义是**无门、无物**，**不是黑屏**。已单列 `A5b` 钉住，免得下次又说错。
4. **★★ 索引与分片是两层数据**：`_index.json` 里 ut 全部房间的 `bg` 都是 `null`，
   真正的 `bg` 只在 `_zone.ut.rooms.json` 分片里。
   若用 `load_index` 的摘要去判断"有没有背景"，会得出"全部都没有"的假结论 ——
   **用错入口 = 假问题**（与第89轮 C 段首版同型）。必须走 `load_scene`。
5. **★ 判据方向写反**：`check124.C5` 第一版把 `_OPENING` 建成 `{下标: scene_id}`，
   而 `_rid_of` 是 `{scene_id: 下标}`，`==` 永远 False。
   ⇒ **比较两个 dict 前先确认键是哪一头**。
6. **`room_area1` 的 `original_room_id` 是 4，不是 0** —— 这条事实推翻了我上一轮的
   推断（"两间房下标都是 0"）。**推断不能当证据**。
