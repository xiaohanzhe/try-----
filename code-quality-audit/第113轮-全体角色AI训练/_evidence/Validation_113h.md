## 1. 根因（实测，不是推断）

### 1.1 字体：全仓库只有一个

| 位置 | 结果 |
|---|---|
| `ralsei_pet/` 下递归找 `.ttf/.otf/.woff/.fnt` | **0 个** |
| 仓库根 `普通字体.ttf` | 1,907,088 B（FZXS12 像素字体） |

字体出口只有一处：`dialogue_ui._load_ralsei_font()` → `QFontDatabase.addApplicationFont()` →
`_ralsei_font(point_size, bold)`。`_PIXEL_NOAA=True` 时 `setStyleStrategy(QFont.NoAntialias)`。
**没有按角色切字体的能力** ⇒ 「全大写」不能靠"换一套大写字体"，只能靠**逐条消息转写**。

### 1.2 「全大写」为什么逼出英文

- 中文没有大小写。人设写「你说话时全部使用大写字母」，中文**执行不了**；
  模型为了满足这条唯一的办法就是**改说英文**。
- 实证：`hy_guardener` 中文占比 **0.00**（36/36 轮全英文）；`hy_axis` 加中文规则后
  0.00 → 0.52，但 `hy_guardener` 压不住 —— 说明"加一条中文规则"只是碰运气，
  没有消解冲突本身。
- 不能用 `QFont.setCapitalization()`：那是**控件级**属性，会给整个
  `dialogue_content` 设上，把历史区里别人说过的话一起改掉。

### 1.3 这不是 1 个角色的问题

全库扫「大写」表述，**要求输出层全大写**的共 6 个角色、22 处：

| 角色 | 出处 |
|---|---|
| `hy_guardener` | 【禁忌】「对话全部以大写字母输出」；结尾「你全部使用大写字母说话」 |
| `hy_axis` | 【核心性格】「正常状态下你全部使用大写字母说话」；【禁忌】「不要使用小写字母」 |
| `os_rowbot` | 【语言风格】「你的说话方式全部使用大写字母」；【禁忌】「所有对话都必须是大写的」 |
| `ot_papyrus` | 【禁忌】「Papyrus 说话时全部大写。这是最重要的规则」 |
| `ut_papyrus` | 同上（Outertale 版同源） |
| `queen` | 【核心性格】「每个单字都大写」；结尾「你的语言是平板的、全大写的」 |

⇒ 逐份改人设＝6 份 × 2~6 处，且**英文台词是原作依据，不许删**。
这正是用户说的「别只顾着三人」：必须换机制。

## 2. 机制：两轴正交

### 2.1 `assets/npc/_kinds.json`（schema_version 2）

```
kinds（活人感）: hy_guardener / hy_axis / os_rowbot / os_prophetbot / os_prototype / os_kelvin = machine
caps（显示层全大写）: hy_guardener / hy_axis / os_rowbot / ot_papyrus / ut_papyrus / queen
```

**两轴独立，各有反例**（这是本轮最要紧的结构）：

| 角色 | kind | caps | 说明 |
|---|---|---|---|
| `ot_papyrus` / `ut_papyrus` | human | **true** | 骷髅，要有人味，但原作全大写 |
| `os_kelvin` | machine | **false** | 取暖器机器人，不大写 |
| `os_silver` | human | false | 人设原文就是要它「像人一样思考、有情感」—— 负控制样本 |
| `rouxls` | human | false | 只有「随机大写强调」，整条渲染会演成另一个人 |

⇒ 用 `kind == 'machine'` 当大写判据，会**同时**漏掉 Papyrus、多算 Kelvin。

### 2.2 代码改了什么

| 文件 | 改动 |
|---|---|
| `modules/npc_persona.py` | 新增 `CAPS_RULE`（覆盖句）、`load_caps()`、`caps_of()`；`build_system_prompt()` 在 `speak_rules_for()` 之后按 `caps_of(npc_id)` 追加覆盖句，**未登记的一字不加** |
| `modules/dialogue_ui.py` | `_kind_machine()` → `_caps_on()`（改查 `caps_of`）；`add_dialogue` 的 NPC 分支按 `_caps_on(speaker)` 做 ASCII 大写化（`str.maketrans`，中文/标点原样；在 `_html.escape` **之前**做，否则 `&amp;` 会变 `&AMP;`） |
| `assets/npc/_kinds.json` | 新增 `caps` / `caps_why` / `caps_deliberately_excluded` |

`CAPS_RULE` 原文：

> 人设里凡是要求你「全部大写」「不要用小写」的地方，说的是**显示效果**：屏幕上会自动把字母转成大写，不需要你为此改变说法。你一律用中文说话，不要因为这条要求改说英文；人设里那些英文台词是原作依据，用来让你理解语气，不要照搬。

**为什么放在机制层而不是人设层**：一份覆盖句对所有登记角色生效，改一次即可；
人设里的英文台词（语气依据）一个字都不用动，避开"为了本地化把角色改坏"。

## 4. 事故：E 盘掉线导致 10 个套件假 DIFF

### 4.1 症状

全量 G2：`PASS=5484 FAIL=0 套件=106`，但 **10 个套件 DIFF**，而 PASS/FAIL 计数**一条没变**。
逐条看 `.diff.txt` 都在同一位置多一行：

```
<TS> [WARNING] ralsei_pet.desktop_interaction — 获取存储分区信息失败: [WinError 1] 函数不正确。: 'E://'
```

### 4.2 根因（直接查盘确认）

```
os.path.exists('E:/')   → False
os.listdir('E:/')       → OSError(22, '函数不正确。')
```

**E 盘整体掉线**（exFAT 外置盘）。仓库在 C 盘、不受影响；但产品每次枚举分区就多打一条告警。
补充：约 20 分钟后复查 `os.path.exists('E:/')` 又变回 **True** —— 是**瞬时掉线**，
所以这行告警的"有/没有"完全由外部设备状态决定，逐字节基线对它必然假红。

### 4.3 为什么 `.diff.txt` 会把人骗得更惨

`_out/<suite>.baseline.txt` 是**陈旧文件**（本机实测有 10-06 的），
run_all 自己的 docstring 就写着「它不是基线快照的可靠来源」。
于是 `check89` 的 diff 显示成「baseline 有 9 扇门 / now 有 4 扇门」——
看着像 109~111 轮的门改造没进基线，其实那是 10-04 的旧文本，**真判据只有 sha**。

⇒ 结论：**看 `.diff.txt` 会归因错误，必须拿当前 `normalize()` 重算 sha 与 `baseline.json` 比。**

### 4.4 修法

`run_all.py` 加 `_STORAGE_PROBE_NOISE`，整行剔除，并在注释里写明代价
（"存储盘掉了"在这条 stdout 上看不见了；真正守数据落点的是 `data_store` / `npc_memory` /
`check67` / `check73` 的隔离目录断言）。

**正则实测过真行**（不靠"看着像"）：

```
[OK] 真行(E盘)            match=True
[OK] 真行(D盘换盘符)      match=True
[OK] 不该被吃0            match=False
[OK] 不该被吃1            match=False
[OK] normalize 后该行消失=True 对照行仍在=True
```

加归一化后复跑那 10 个套件：**8 个立刻 IDENTICAL**，剩 2 个是真欠账（见 §5）。

## 6. 第二个结构性缺陷：`check77` 直接读外置盘

修完 §4 再跑，`check77` **新**抖成 DIFF，而它上一轮还是 IDENTICAL。差异：

```
-[SKIP] ut  原作转储不在（E:/Download/_extract61/_data/undertale/ut_rooms.json）⇒ B0..B2 跳过
-[SKIP] uty 原作转储不在（…undertale_yellow/ut_rooms.json）⇒ B0..B2 跳过
-[…] PASS=29
+[PASS] B1 ut：原作 338 间与原版逐条全等，不符 0
+[PASS] B1 uty：原作 287 间与原版逐条全等，不符 0
+[…] PASS=31
```

### 6.1 根因

`check77.py` 里硬编码 `SRC_DIR = r'E:\Download\_extract61\_data'`：
**盘在 ⇒ 跑 B 段（31 条）；盘不在 ⇒ SKIP（29 条）**。
录基线那一刻盘掉线（记成 SKIP），复跑时盘回来了（变成 PASS）⇒ 基线永久抖动。

这不是"环境噪声"，是**依赖了不该依赖的东西**。记忆铁律本来就写着：
> 回归套件不许依赖临时区/外部盘 ⇒ **蒸馏进仓库**。

### 6.2 修法

1. 两份 `ut_rooms.json`（ut **311,173 B** / uty **329,523 B**，合计 ~640 KB）
   复制进 `code-quality-audit/第77轮-场景补齐与自主生活/_evidence/src61/{undertale,undertale_yellow}/`。
2. `check77` 改成 `_SRC_CANDIDATES` 列表 + `_resolve_src(sub)`：
   **仓库内优先**，外置盘只作兜底；两级都没有才 SKIP，且 SKIP 文案会把两条路径都打出来
   （免得后人以为"又是 E 盘掉了"而放过仓库缺件）。
3. `--update` 建立新基线（PASS=31）。

### 6.3 负控制（关键，否则等于什么都没证明）

盘在的时候，**原代码**也是 PASS=31 —— 只跑这一遍证明不了任何东西。
所以把兜底路径拆掉再跑一次：

```
替换外置盘路径 1 处            ← 恰好 1 处，0 处=没拆到
exit = 0
SKIP 行数 = 0
末行 = 第77轮 跨作品场景迁入锁：PASS=31 FAIL=0
结论：负控制通过 —— 外置盘缺席仍全绿
```

⇒ 基线抖动源真的被移除了，不是"这次运气好盘在"。

## 8. 训练验证：覆盖句**压不过**人设里的英文示例语料（负结果，两次实测）

### 8.1 第一次（弱措辞）

`train30.py --only hy_guardener --turns 12 --force`（12 分 52 秒）→ `verify113g`：

```
旧  12 轮  中占比 0.00   caps 12.71   硬违规 12/12
新  12 轮  中占比 0.00   caps 11.67   硬违规 12/12
```

两件事先被确认：

- **`CAPS_RULE` 确实进了 prompt**：直接重算 `build_system_prompt`，
  `含 CAPS_RULE = True`，位置 `9923 / 10036`（末尾），`caps_of=True`、`kind=machine`。
- **`verify113g` 那条判据自己失效了**：它写死「四句人话必须在 prompt 里」，
  可 machine 档是**用机段替换**那四句（互补不是叠加）⇒ `hy_guardener` 必然报
  「缺：四条」，**判据红而产品对**。已改成按档位分流（human 要四句且不许机段 /
  machine 要机段且四句必须不在），并补一条「caps 角色必含覆盖句」。

### 8.2 第二次（强措辞，明确写出优先级）

推测：人设里「不要使用小写字母」是**命令句**，我那版是**解释句**（"说的是显示效果"），
7B 服从命令。于是把覆盖句改成：

> 关于说话方式，下面这条**优先于人设里所有关于大小写的说法**：你一律用中文说话，这是硬要求。
> 人设里说的「全部大写」「不要用小写」，指的是屏幕上呈现出来的样子 —— 显示层会自动把字母
> 转成大写，不需要你为此改变说法，更不要为了满足它改说英文。人设里那些英文台词是原作依据，
> 只用来让你理解语气，不要照搬，也不要跟着它用英文回答。

重训 12 轮（11 分 47 秒，prompt 10592 字）→ **中文占比仍然 0.00**：

```
#1 [caps] HE-HELLO THERE. WAS IT YOU WHO DISTURBED THE FLORA? I ASK YOU TO PLEAS…
#3 [caps,ellip] ...HE-HELLO THERE. I AM AWAKENED BY THE LIGHT AND BEGIN MY PATROL…
```

### 8.3 结论（可复用，别再试第三版措辞）

> **7B 跟的是语料的语言，不是末尾一句指令。**

`hy_guardener` 的人设 9,494 字里，【示例反应】有 **10 段整段英文长对话**、
【禁忌】【核心性格】还有大量英文短句。在这种密度下，末尾 100 余字的覆盖句
在两次不同措辞下都是 0.00 ⇒ **指令层这条路已经走到头了**。

两条真正可行的路，都需要口径裁定（**都不在"直接用字体"能覆盖的范围内**）：

| 方案 | 做什么 | 代价 / 风险 |
|---|---|---|
| A **译示例** | 把 caps 角色的【示例反应】英文台词译成中文（内容/语气不变，只换语言） | 等于改人设语料；与用户「他不是有字体吗，你直接用就好了」有张力，需明确授权 |
| B **接受英文** | 不动人设；渲染层已把 ASCII 转大写，视觉上"全大写"仍然成立 | 中文占比判据对这批角色永远 FAIL ⇒ 应把它们从「中文占比」判据里**显式豁免**，而不是每轮报红 |

⚠️ 在裁定之前：**不要开全量 77 人训练**。`verify113g` 的结论行已经写着「有 1 项不达标，不要开全量」。
