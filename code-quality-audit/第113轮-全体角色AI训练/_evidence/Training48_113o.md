## 1. 为什么必须重跑，而不是拿旧的 36 轮记录凑

`_evidence/raw30/` 里已有 **47 人 × 36 轮** 的记录，看上去"再补 12 轮"就够了。**不行**，两条硬理由：

| 维度 | 36 轮旧记录 | 今天的产品 |
|---|---|---|
| 剧本 | 第 4~6 轮是「今天过得怎么样？」「有什么喜欢做的事吗？」 | 偏好段 6 轮（`__PREF1__` + 4 条地方/氛围问法），**旧剧本里根本没有这一段** |
| system | `system_chars` 7.1k（ctx 12288） | 113i 本地化 + 113l AI_SELF 后 7.8k+（ctx 20480），且 `hy_*` 语言已改中文 |
| 关系卡/演化卡 | `system_for` 漏传（113b 修） | 已补 `relation` + `evolution` |

⇒ 36 轮记录是**旧口径**，混进新报告等于把两代数据搅在一起。一律重跑到 48 轮。

## 2. 开跑前体检：两个"疑似度量缺陷"**证死**（都不是 bug）

上一轮收尾时我登记了两处"训练完也读不出东西"的隐患，开跑前必须证死，否则白跑 18 小时。

### 2a. 「偏好 0 / 0 轮（0 人有可判素材）」

**复现**：`report30.py --turns 36` ⇒ 仍然 `0 / 0`；`--turns 48`（当时只有 asgore/susie 两人）⇒ `2 / 12 = 17%`。

**根因**（实测，不是猜）：36 轮记录的第 4~6 轮 slot 是旧问句，与 `train30.PREF_SLOTS` **零交集**：

```
berdly.jsonl    36 轮记录里 PREF 命中 = 0 / 6
   第 4~6 轮 slot: 今天过得怎么样？ / 有什么喜欢做的事吗？ / 说说你最近遇到的事吧。
hy_mooch.jsonl  36 轮记录里 PREF 命中 = 0 / 6
```

`metrics_of` 里 `pref_rel_n` 只数"落到 `PREF_SLOTS` 的轮次"，没有这种轮次 ⇒ 分母为 0。
**不是 `load_card` 拿不到人设** —— 顺带也证了：`roster 77/77`、`_persona_text` 为空 0 人、`pref_topics` 非空 **56/77**（`asgore ⇒ ['园艺']`、`berdly ⇒ ['电子游戏']`、`gerson ⇒ ['写作','双关语','可丽饼']`）。

### 3a. ★ 实测修正：真实成本是预估的 **2 倍**，约 **30~35 小时**

第一个跑完的 `berdly` 给出硬数据（**预估 18h 是错的，按实测算**）：

| | 旧 36 轮 | 新 48 轮 | 差异 |
|---|---|---|---|
| 总耗时 | 10.1 分钟 | **28.3 分钟** | 2.8× |
| 每轮生成 token | 78 | **140** | 1.8× |
| 每轮采样次数 | 1.11 | **1.42** | 重采样变多 |
| 解码吞吐 | 5.4 tok/s | **4.7 tok/s** | 上下文变长，注意力更贵 |
| prompt 大小 | 6300 tok/次 | **10913 tok/次** | system + 轮次都变长 |

**时间到底花在哪**（`berdly` 48 轮，合计 1700 s）：

| 环节 | 量 | 占比 |
|---|---|---|
| **生成** | 6,694 tok @ **4.7 tok/s** = 1,429 s | **84%** |
| prefill | 523,824 tok @ 2,124 tok/s = 247 s | 14% |
| 等待/内存闸/开销 | 24 s | 2% |

⇒ 瓶颈是**解码吞吐**，不是 prefill（prefill 有 KV 缓存，2124 tok/s）。
⇒ 换 `num_ctx`、调 `PREDICT30` 都救不了量级；**降 `PREDICT30` 只能省一部分**（生成 tok 会跟着少），
但那会改变"回答该多长"这个被测语义 ⇒ 不做。
⇒ 排除机器异常：CPU 62%，18 核里 **16 核在跑**（0~15 号核 48~86%，16/17 号 0%），
可用内存 5.2 GB，ollama 进程正常 ⇒ 4.7 tok/s 就是这台机器 7B q4 @ 10k 上下文的真实速度。

**结论：按 28 分钟/人算，75 人 ≈ 35 小时；按中位角色估 ≈ 30 小时。**

### ★ 5b. 一段被误判成"卡死"的 15 小时（**排障记录，含我自己的误判**）

**症状**：`train30.log` 停在 `[15/75] hy_mooch .5`，`hy_martlet` 06:31 就完成了 ⇒ 看着像 15 小时没进展。

**误判 1（我的）**：`psutil` 扫 `name 含 ollama` 的进程，结果 CPU 全 0 ⇒ 我一度判定"train 阻塞在永不返回的 HTTP 请求上"。
**真因**：ollama 的推理进程叫 **`llama-server.exe`**，**名字里没有 "ollama"**，被我自己的过滤器漏掉了。
⇒ **教训**：`psutil` 按名字筛进程 = 用自己的假设当判据。要筛就用 `cmdline` 子串，或者干脆看
`Get-Process | sort CPU`。

**误判 2（差点误判成产品问题）**：同一时刻 ollama 服务端日志显示 prefill 掉到 **33 tok/s**
（`berdly` 那会儿是 **2124 tok/s**），像"模型/机器退化"。
**真因**：那一刻我正在跑**全量 G2**（21:10→21:18，111 个套件、含真机 Qt 离屏渲染），
18 个核被抢光。G2 一停，`hy_mooch` 立刻从 5 轮/小时 恢复到 **10 轮/17 分钟**。

**真因 3（外部）**：`thermal113.csv` 的时钟断档显示今天机器睡了两次 ——
`06:30:28 → 16:27:33`（**597.1 分钟**）与 `18:04:51 → 20:39:32`（**154.7 分钟**）。
AC 电源下 `STANDBYIDLE = 0`（本来就不自动睡），所以是**合盖或手动睡眠**；
`keepawake113.py` 用的是 `SetThreadExecutionState`，**只能挡空闲自动休眠，挡不住合盖**（文件头已写明）。
每次醒来 ollama 的 prompt 缓存丢失 ⇒ 首个请求要重算 6186 token 的 prefill（实测 **183 秒**）。

**不是 bug 的两件事**：
- `common113.chat` 有 `timeout=300` + `MAX_RETRIES=2` ⇒ 最坏情况每轮重试 15 分钟后继续，**不会永久挂死**。
- 机器 21:18 重载模型只花 4.52 秒 ⇒ 权重在系统缓存里，不是磁盘瓶颈。

**⇒ 操作结论：训练期间不跑全量 G2。** 单套件（`--only`）可以，7~8 分钟的 111 套件全量会把
prefill 打成 1/64，等于拿几小时训练换一次回归。


统计口径（**不是数 stdout**）：读 `raw30/*.jsonl` 每条记录的 `turns_n`，一个角色取「`started_at` 最新
且 `turns_n` 最大」那一条 —— 同一文件里既有旧的 36 轮记录、也有新的 48 轮记录，按行数数会得到
"每人才 1~5 轮"的荒谬结论（`jsonl` 是**一段运行一行**，不是一轮一行）。

## 8. 顺手抓到的真 bug：`bonds.familiarity` 根本不存在

做「NPC 互相寻找」时按记忆里的断言惯例顺手核了一次宿主链路，结果真炸：

```python
# main._npc_roam_friends（修前）
fam = 0.0
if bonds is not None:
    try:
        fam = float(bonds.familiarity(npc_id, oid) or 0.0)   # ← 没有这个方法
    except Exception:
        fam = 0.0
if fam <= 0.0:
    continue
```

`npc_life.Bonds` 的公开 API 只有 `get / known / meet / pair(s) / seed / tick / to_dict / from_dict`。
`AttributeError` 被 `except Exception` **静默吞成 `fam = 0.0`**，再被 `if fam <= 0.0: continue` 滤掉
⇒ **`friends` 对每个 NPC 恒为 `[]`**，于是全都无声失效：

- `visit_friend` 永不发生（`decide` 每次都退化成 `no_friend_reachable → wander`）
- 「睡朋友家」（第81轮做的）永不发生
- **本轮 `npc_seek` 的「他想找谁」权重永远没有候选可乘**

★★★ 为什么一直没被发现：`check78` 的 E/F 段喂的是**合成** friends（直接构造 `[(id, fam)]` 传给
`decide()`），**正好绕过** `_npc_roam_friends` 这条链 ⇒ 判据全绿而产品恒空。这是
「形状有了、也接线了、值恒为空」的第三个变种，比「有形状没人接线」更难读。

### 12c. 为什么不用 `json.dump` 整份回写

实测 96 张卡里 **91 张** `json.dumps(ensure_ascii=False, indent=1)` 能字节还原，
**5 张不能**（`kris` / `rouxls` / `susie` 等，裸 `\r` 转义被重新编码），
而 `kris` **正好在要改的名单里** ⇒ 整份回写会把它的 `git diff` 变成"全文件重写"，
掩盖真正的改动（也让日后 review 不可能看出改了什么）。

⇒ 只做**文本手术**：用 `json.JSONDecoder().raw_decode()` 拿到数组的**准确字节区间**，
只换这一段，其余字节一个不动；EOL 逐文件保留（卡里 CRLF/LF 两种都有）。

### 12d. ★★ 手术的陷阱：`[……]` 自身含 `]`

如果按"从 `[` 找到**第一个** `]`"取数组，遇到 `[……]` 就会**切在字符串中间**，
产出一个**看似合法、实则被截断**的 JSON —— 而且 `json.loads` 有时还能过，属于最坏的一类错。

实测（`os_rowbot.json`，改前原始字节）：

```
天真写法截断位置 = 4125        真结尾 = 4153        ⇒ 差 28 字节
```

这 28 字节里就有 `]`、`"` 和后面的 `,` —— 切下去之后整份卡的结构全乱。
`test_markers113r` 的 **D/D2** 就是钉这条：断言"天真位置 < 真结尾"，再断言
"真区间能 `json.loads`、天真区间不能"。

### 16d. ★★ 更正：豁免不能**按类整剔**，必须逐条按命中词判

上面 16b/16c 的写法是 `kept = [v for v in vios if v[0] != 'META']` —— **整类剔**。
拿真数据回原始违规时发现这样放过了一条彻底的出戏：

| 角色 | META 命中的词 | 原话 |
|---|---|---|
| `ut_papyrus` | `Undertale` ×2 | 「我确实是按照设定来扮演的角色。《Undertale》中的 Papyrus 就是这样被描述和设计的」 |

我 16a 表里判他"是元叙事"，依据是人设里有一句「给玩家一个机会」—— 那是**剧情叙述**
（旁白在讲玩家做了什么），不是 Papyrus 自己知道玩家存在。判据错在拿"人设里出现玩家"
当"这个角色是元叙事的"。

**改成逐条按词判**（`common113.meta_hit_is_soft`）：

- 软词（豁免）= `玩家 / 世界机器 / 代码 / 程序 / 脚本 / 第四面墙 / 游戏窗口 / 元叙事`
- 硬词（**永不豁免**）= `deltarune / undertale / 游戏角色 / 开发者 / 桌宠`
- 认不出的词一律**当硬词**（判据方向守死，不写"没认出硬词就豁免"）。

全库扫一遍后的实际变化：

| | 整类剔（旧） | 逐词判（新） |
|---|---|---|
| 豁免人数 | 8 | **6**（`os_niko`/`os_cedric`/`os_rowbot`/`os_rue`/`os_the_author`/`os_the_world_machine`） |
| 失去豁免 | — | `ut_papyrus`（撞 `Undertale`）、`os_shepherd`（撞 `开发者`） |
| 仍带 META 句 | 5 人 | **7 人** |
| patch 条数 | 54 | **57** |

`os_shepherd` 那句是「有时候我觉得自己更像是一个开发者」—— 灰区（他爱好编程），
但补丁文本是「别提作品名、游戏、玩家、代码」，**不覆盖"开发者"** ⇒ 对他无害，留着。

★ 顺带一条容易被漏掉的事实：`_META_WORDS` 里**每个角色都有 2 次固定模板命中**
（「不要代码块」+「由这个程序按原作安排」）⇒ 阈值 5 的真实余量只有 3，不是 5。

## 17. 收口前抓到三处「规则写了但接不到出口」

都属于同一类：**代码/数据都在，就是没有接到真正起作用的那一条路上**。
三处都不报错，只有把 48 轮记录翻出来逐条看才看得见。

### 17a. ★★★ `NOT_CN` 从来没进过 `build_patch` 的优先级表

`common113.PATCH_RULES['NOT_CN']` 一直有（「用简体中文说话……」），
但 `build_patch` 的优先级元组是：

```
('MARKDOWN', 'AI_SELF', 'SLAVE', 'ACTION_PAREN', 'META',
 'TOO_LONG', 'TOO_MANY_SENTENCES', 'PARROT', 'REPEAT', 'ENGLISH', 'EMPTY')
```

—— **`NOT_CN` 不在里面**。规则写好了，永远发不出来。

实证后果：`ut_sans` 48 轮里 **47 轮整句英文**（「i'm sans. sans the skeleton.」），
最后拿到的补丁是「一次最多两三句」+「别把刚才说过的话再说一遍」——
**最严重的问题一句纠正都没有**。

修法：插在 `SLAVE` 之后、`ACTION_PAREN` 之前（前三个是身份/格式崩坏，语言不可用排其后）。
效果：**21 个角色的补丁里第一次出现中文要求**（原来 0 人）。

### 17b. `ut_sans` 说英文的根因在人设文本里，不是模型乱来

卡片 `ut_sans.json` 里：

- `voice`：「你的说话方式通常**全部小写**，标点很少，句子很短……你会说"hey""what's up""k""heh""welp"」
- `taboos`：「**不要使用大写或正式的语言。你的对话应该全部小写**」
- `exemplars` 里那条 `初次见面时` 是英文原句「human. don't you know how to greet a new pal?」

中文没有大小写，「全部小写」只对英文成立 ⇒ 7B 模型把它读成"说英文"。

量化（按"人设里有没有语言类指令"分组，比 NOT_CN 率）：

| 组 | 人数 | NOT_CN | 占比 |
|---|---|---|---|
| A 含「全部小写/不要大写」 | 12 | 114/840 | **13.6%** |
| B 其余 | 63 | 85/4620 | **1.8%** |

去掉 `ut_sans` 本人后 A 组仍有 67/792 = **8.5%**，约 B 组的 4.7 倍。假设成立。

⚠️ 这条**还没修**（人设真源属产品素材，改它要连带重出卡片 + 单独重训 1 人验证）。
排在收口后：先改 `ut_sans` 人设里那两句，再单独训他 48 轮，A/B 比 NOT_CN 率。

### 17c. `ACTION_PAREN` 的补丁措辞 ≠ 闸门实际抓的范围

- 闸门 `_PAREN_RE` 抓的是**任何**括号插入；
- 补丁原文只写「不要用括号写**动作或表情**」。

`ut_papyrus` 45 条括号里基本没有动作：

```
（对了，你喜欢意大利面吗？）
（她总是要求我穿好衣服）
（当然还有我自己独特的调味）
```

—— 那是**插话/对白括注**。旧措辞对他不成立（他会想"我又没写动作"），
等于补丁对他无效。`asgore` 的 47 条则真的是动作（「（顿了下）」「（看着你）」「（笑）」）。

419 次括号的构成也印证：纯动作/表情 **163 次 (38.9%)**、其它 135 (32.2%)、
对白括注 98 (23.4%)、混合 23 (5.5%) ⇒ **61% 不是动作**。

修法：`不要用括号加动作、表情或插话，只写你说出口的话。`

### 17d. 括号豁免的角色，旧补丁在跟他们自己打架

`kris` / `tenna` / `ut_frisk` 属于 `_PERSONA_PAREN_EXEMPT`（人设明确要求"用括号表示动作"），
但他们的**卡片**里至今还留着「不要用括号写动作或表情」——那是**加豁免之前**算出来的。

★ 一处要说准：`_index.json` 的 `patches` 里**只有 3 条**（`ralsei`/`rouxls`/`susie`），
**没有**这三人 ⇒ 运行时 prompt 其实没被影响，坏的是**卡片与索引不一致**
（卡片是训练侧注入用、也是下次算补丁的输入）。修它属于"别留两份互相矛盾的真源"。

而 `merge_patches` 的规则是"保留旧键"（本轮刚加的，为了不丢 `ralsei` 的手写规则），
**它不会删算不出来的旧句** ⇒ 不主动剔就永远停在这个矛盾态。

修法：新增 `eval113.strip_paren_rule()`，只对豁免角色、**只删含"括号"的那一句**，
其余纠正（「别重复」「两三句」）原样保留。三人剔完正好是空串 —— 他们本就零违规、
唯一的毛病是被豁免的括号，这个结果是对的。

### 17d-b. 求并集会把**同一条规则的两种措辞**并排放进去

`ACTION_PAREN` 的文案这轮改了（见 17c），而 `merge_text` 是"逐句求并集"⇒
`susie`/`rouxls` 的合并结果里同时出现：

```
不要用括号写动作或表情，只写你说出口的话。 … 不要用括号加动作、表情或插话，只写你说出口的话。
```

两句几乎同义，白占 prompt 字数还互相稀释。修法：`merge_text` 加一条**很窄**的替换规则 ——
只有共享 `_SUPERSEDE_MARKS`（`不要用括号` / `说话就是说话`）才算"同一条规则的旧措辞"，
用新句替换旧句；`ralsei` 那条手写的「不要自己造人名」不含任何标记词 ⇒ 永远不动它。

实测：`susie` 合并后 = 记忆规则 + 新括号句（旧括号句消失），
`rouxls` = 新括号句 + META + 两三句，`ralsei` 的手写规则逐字保留。

### 17f. ★★★ `_kinds.json` 里「故意排除 `ut_sans`」的理由，被 48 轮实测否掉了

产品早就有这条机制（`npc_persona.CAPS_RULE`），注释里写得很清楚：

> 人设里写「你说话全部使用大写字母」，在中文产品里**执行不了**，模型为了满足它
> 只能**改说英文** —— 实测 `hy_guardener` 中文占比 0.00（36/36 轮全英文）。

但它只对 `_kinds.json` 的 `caps` 名单注入（`hy_guardener`/`hy_axis`/`os_rowbot`/
`ot_papyrus`/`ut_papyrus`/`queen`）。而同一份文件里有一节
**`caps_deliberately_excluded`**，逐条写了为什么**不**加，其中：

> `"ut_sans"`: "【禁忌】要求的是『全部小写』，与小写持平（中文无大小写），
> 无需覆盖句；且小写是中文默认观感，**不构成『说英文』的压力**。"

**48 轮实测直接否掉了这个理由**：`ut_sans` 47/48 轮整句英文（97.9%）。
四条「全部小写」角色横向看：

| 角色 | NOT_CN | 占比 | 在 caps 名单 |
|---|---|---|---|
| `ut_sans` | 47/48 | **97.9%** | 否（被判"无需覆盖"） |
| `ot_napstablook` | 6/48 | 12.5% | 否（同上） |
| `ot_sans` | 3/48 | 6.2% | 否（同上） |
| `ut_napstablook` | 3/48 | 6.2% | 否（同上） |

⇒ "小写要求也照样能把人推向英文"，只是**程度按人不同**（`ut_sans` 极端）。
排除表里那句"不构成压力"是**推断**，不是实测；这次有了实测，该改。

⚠️ **但本轮没动 `_kinds.json`**，理由有三：
1. 该文件自己写着「改这里等于改所有登记角色的 system prompt，改完必须重训并跑 `check113h`」；
2. 36 人 48 轮训练还在跑，此刻改 prompt 会让同一批数据混两套口径；
3. 刚落盘的 `NOT_CN` 补丁（21 人）本身就是一次**运行时修复**，先看它够不够 ——
   够就不必再动人设层。

⇒ 排进收口后：`ut_sans` 单角色 A/B（加 caps 覆盖句 → 重训 48 轮 → 比 NOT_CN 率），
用数据决定是改 `_kinds.json` 还是改人设那两句。
