# 第125轮 · Deltarune 五章的 D 门（−2）与 X 门（表驱动）补齐

> 一句话：**ch3~ch5 路由稀疏不是"没数据"，是第44轮把两种门判错了** —— 本轮用第44轮自己那把尺复核，
> 补 139 条原作边，五章「有出边的场景数」105/127/23/22/20 → **116/137/35/32/31**，桌面可达 199 → **215**。

---

## 1. 缺口是什么

第124轮末的可达账（`check124` D 段）暴露：ch1~ch5「有出边的场景」只有 **105/127/23/22/20**，
而场景数是 **128/236/187/261/201** —— ch3~ch5 尤其稀（23/187、22/261、20/201）。

先排除三种常见解释：

| 猜测 | 实测 | 结论 |
|---|---|---|
| 没数据 / 场景本身没门 | `_room_graph.json` 里 ch1~ch5 有 **782** 条边 | ✗ |
| 边被去重吃掉了 | 产品 ch1~ch5 段 **443** 条 | 只转出 **56.8%** |
| 端点没登记 | 782 条里仅 **15** 条端点未登记 | ✗ |

⇒ 差在**门型**：第44轮的生成器 `gen_routes44.py` 只编三种位移门
`obj_doorA +1` / `obj_doorB −1` / `obj_doorC +2`，并在 docstring 里**明确拒收**
`obj_doorD` 与 `obj_doorW/X`。被拒收的这两类，在证据里分别是 **78 / 363** 条边。

## 2. ★★ 第44轮为什么拒收（错在哪）

它的原话是：

> `obj_doorD`：位移未定，实测 **+2** 只有 33%，证据不足，不猜
> `obj_doorW`/`obj_doorX`：表驱动双向，需读对象代码

而 `第42轮/_tools/graph42.py` 的机制表（同样来自 Alarm 反汇编）写的是：

```
obj_doorD[_musfade] → room_goto(room_previous(room_previous(room))) → index − 2
obj_doorX/X_musfade → 表驱动 {src_room: dst_room}
```

**它不是"没证据"，是第44轮没读对象代码、只试了 `+2` 这一个先验。** 33% 正是"用错位移"的命中率。

## 3. ★★ 本轮怎么验的（同一把尺，不换标准）

判据沿用第44轮对 A/B/C 用过的**那一条**：**目标房必须含 `obj_marker<同字母>`** ——
位移只是先验，**落点是独立验证**。数据源是仓库内第42轮蒸馏的证据
（`_evidence/ch*_inst42.json` 实例 + `ch*_conn42b.json` 的查表项）。

| 组 | 有目标的实例 | 命中同字母 marker | 命中率 | 处置 |
|---|---|---|---|---|
| D（−2） | 74 | 71 | **95.9%** | ✅ 收 |
| X（表驱动） | 94 | 94 | **100.0%** | ✅ 收 |
| W | 97 | 0 | **0.0%** | ❌ 不收 |

★ W 的 0% 查清了原因：marker 名是**小写** `obj_markerw`。换成小写重测 **60.2%（115/191）**，
换 `obj_markerX` 重测 **84.3%（161/191）** —— **两套写法都到不了 100%** ⇒
"证据不足不猜"这条纪律照旧，W 一条不写。

★ D 的 3 个例外逐条留档（见 §5），**如实不写**，不为了凑数放宽 marker 闸。

## 4. 改了什么

新增生成器 `_tools/gen_routes125.py`（准入三闸，缺一不写）：

1. **机制已证**：D = −2（第42轮 Alarm）｜ X = 表驱动（读 `Alarm_2` 的 `{src: dst}`）
2. **落点自证**：目标房含 `obj_marker<同字母>`
3. **产品侧不冲突**：同场景同 `when_door` 只一条；新段 priority 从 **5000** 起

产出：**139 条**（D **56** / X **83**），priority **5000~5138**（连续），
逐章 ch1 46 / ch2 26 / ch3 24 / ch4 21 / ch5 22。

`_original` 两种形状：
- D 条：`{chapter, door_letter, room_delta: -2, src/dst_room_name, src/dst_room_id, via, marker}`（**不带 `kind`** ⇒ 走老锁现成的位移分支）
- X 条：`{chapter, door_letter, kind: 'delta_door_table', table, via, marker, src/dst_room_name, src/dst_room_id}`

格式逐字节保持：`ensure_ascii=False, indent=2` + CRLF + **无尾换行**。
`_routes.json` 857,656 B / 1,392 条 → **985,694 B / 1,531 条**（CRLF 27,663 / 裸 LF 0 / 尾 `}\r\n}` / 无 BOM）。

## 8. 踩坑（7 条）

1. ★★★ **`name` 是显示名、`name_raw` 才是原作房名**。第一版生成器把 `_original.src_room_name` 写成
   `我的城堡镇·area_1`，`reason` 里还拼出「我的城堡镇·我的城堡镇·area_1」（1,002 个场景 `name` 已含区名）。
   实测：`name_raw` 与图的 `src_name` **相同 686 / 不同 0**；89 个锚点场景 `name_raw` 为 None。
2. ★★ **用 `name` 映射会"静默 0 命中"**：按显示名查原作房名 ⇒ 782 条全部"缺 src"却不报错。
   必须按 `original_room_id`。这一坑第124轮已经踩过一次（`load_index` 摘要判 bg），本轮换了皮再犯。
3. ★★ **证据里有 20 条重复边**（同一扇门被数了 N 遍，最多 4 行，逐字段一致）。
   第一版没去重 ⇒ 159 条，其中 20 条是冗余。去重键定成三元 `(场景, 字母, 目标)`，
   且"同键但 src/dst 不同"直接 `SystemExit`（那是真冲突，必须人工看）。
4. ★ **不要把"同一对房间"当重复**：第一版加了 `(scene, to)` 去重闸 ⇒ 159 砍到 155，
   砍掉的 4 条全是"另一扇门也去那"的真连接。
5. ★★★ **例外清单不许凭印象写**。我把 3 条 `no_marker` 记成 `263→261 / 34→32 / 90→88`，
   真值是 `263→261 / 55→53 / 34→32`。`90→88` 是"端点未登记"。**判据当场把它打红** ——
   这次报红不是产品坏了，是**我的记录坏了**。
6. ★ **`check105._OLD` 的旧选择器是"必然越走越窄"的写法**：第122轮排 ut、第125轮又要排 ch1~ch5 段。
   换成段位分母后，以后新增段不会再破。
7. ★ **生成器里 `meta.note` 的 `%` 格式化**踩过 `100%%` + 参数个数不匹配的 `TypeError`；
   改成字符串拼接（note 里直接写 `100%`），别在说明文本里用 `%` 走格式化。
8. ★★★ **"恒真判据复查"这个判据自己也漏了**：本项目有两套 harness 约定 ——
   `ok(cond, msg)`（条件是 **args[0]**，见 check105）与 `check(desc, cond, …)`（**args[1]**，见 check124/125/verify_*）。
   复检脚本第一版只查 `args[1]` ⇒ `ok(True, u"x")` 这种**一条都抓不到**，而 ④a 还显示绿色。
   是 ④b 的**正控制**（合成四条、期望恰好两条命中）把它逮住的。已改成两处都查。
