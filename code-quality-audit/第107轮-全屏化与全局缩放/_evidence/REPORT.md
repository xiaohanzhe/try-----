## 3. 三条技术要点

### 3.1 `fit_fullscreen` 的数学与那个 `<=`
`fit_fullscreen(view_w, view_h, ratio=4/3) -> (w, h, ox, oy)`，算法 = **屏幕内最大的 ratio 内接矩形 + 居中偏移**。

```
w_by_h = view_h * ratio
if w_by_h <= view_w:   # 高是限制轴：上下顶满、左右留黑边
    h = view_h; w = round(w_by_h)
else:                  # 宽是限制轴：左右顶满、上下留黑边
    w = view_w; h = round(view_w / ratio)
ox, oy = (view_w - w)//2, (view_h - h)//2
```

★★★ **限制轴判据必须用 `<=`，不能写 `max`**：写 `max` 会让结果**溢出屏幕 = 裁掉画面**，
而不是"留黑边"——这是用户口径的反面。`mutate107` 用 `min → max` 的变异体实测复现了溢出（真红的负控制）。

实测五组（逐值锁进 `check107` A 段）：

| 屏幕 | `(w,h,ox,oy)` | 黑边 |
|---|---|---|
| 2560×1600 | `(2133,1600,214,0)` | 左右各 214 |
| 1920×1080 | `(1440,1080,240,0)` | 左右各 240 |
| 800×600 | `(800,600,0,0)` | 零（恰好 4:3） |
| 1600×2560（竖屏） | `(1600,1200,0,680)` | 上下各 680 |
| 1024×768 | `(1024,768,0,0)` | 零 |

非法输入返 `None`；**零依赖纪律**（顶层禁 Qt、禁项目内 import、禁函数内 import），`check107` F 段 AST 三重判。

### 3.2 缩放的耦合方向（我曾写反一次）
★★★ **正确模型**：`camera.scale = out_w / 320`（由**屏幕**决定），`scoped_size()` **恒 320×240**。
即"画面铺满屏幕、可见范围不变" —— 这是**场景放大**，不是镜头拉近。
★★★ **错误方向**（曾误写）：`scoped_w = 320/k`，那是镜头拉近。

宠物渲染倍率同源：`_cached_scale_factor = camera.scale × pet_scale`
（该字段自第44轮起**从未被赋值**、恒走默认 2.0；本轮接成真源）。
实测 2560×1600 ⇒ `(2133,1600)` @ scale 6.666；离屏 800×600 ⇒ @ 2.500
（Ralsei 贴图 41px × 2.500 = **102px** = 屏上房间高的 17.1%，**与原作比例一致**）。

`ui_scale() = (pet_scale / PET_SCALE_DEFAULT) ** 0.5`，钳 `[0.5, 3.0]`。
⚠️ 用**平方根**而非线性：线性会在大档位把 UI 撑得比窗口还大。

### 3.3 画布铺满 + 固定摆位（"不是跟随移动的窗口"的落地）
- 画布铺满**主屏物理尺寸**（`_primary_screen_size()`，非多屏合并），**固定摆主屏原点**。
- ★★★ **废弃第89轮的"居中 + 四向钳制"**：`_place_scene_layer` 零 `max/min` 调用。
- 摆位后**必须显式 `repaint()`**；`as_window=True` 下**禁 `lower()`**。
- 桌面透明／房间不透明：`_scene_is_transparent()` ⇒ `bg == TRANSPARENT_BG`；
  `set_opaque_bg(True)` 时 `paintEvent` 画**不透明黑**；
  ★★★ `except` 块**必返 `False`**（AST 定点判：`ExceptHandler` 内 `return False` ≥1 且 `return True` == 0）。
- ★★★ `paintEvent` 守卫**必须真消费**：`if False and self._opaque_bg:` 这类短路会**绕过整个不透明逻辑**
  （由 `mutate107` M8 逼出来，判据改走 **AST 判真 `If.test` + body 真调 `fillRect`**）。

## 4. ★★★ 收口：`s7_event_speech` 三条 FAIL = **夹具漂移（产品无缺陷）**

### 现象
全量 G2 报 `s7_event_speech` 的 D2/D2b/D2c **三条 FAIL**，且**不在第107轮预期漂移清单里**。

### 归因（取历史版比对确认）
第75轮（`f43dafb`）按用户裁定关掉了思考占位（`dialogue_ui.AI_THINKING_PLACEHOLDER_ENABLED = False`），
「正在等回复」改由**显式状态位 `_ai_pending`** 承担；
而套件的 `_Dui` 桩**两处都没跟**（既无 `_ai_pending`、`_ai_thinking_on` 又写占位串）
⇒ 产品 `_event_ai_ready` 的**兼容分支** `if getattr(dui,'_ai_pending',None) is None:` 命中
⇒ 回落旧判据 `typing_text == AI_THINKING_PLACEHOLDER`
⇒ 命中**桩自己刚写的占位** ⇒ 判"主人等回复" ⇒ 事件让路走罐头 ⇒ 分片零到达 ⇒ 三条连锁 FAIL。

### 处置（**只改夹具，产品代码一个字节没动**）
`_Dui` 四处对齐：① `__init__` 补 `_ai_pending=False`；② `_ai_thinking_on` 改 `_ai_pending=True` + `typing_text=''`；
③ `add_dialogue` 复刻 `if speaker != 'user': self._ai_pending = False`
（★ **必须排除 `user`**：用户回显发生在 `chat_with_ai()` **之前**，无差别清 = 请求发出那一刻自己抹掉等待位）；
④ `stream_delta` 非 None 时清 `_ai_pending`。D1c 判据同步到第75轮口径。
结果 **139 PASS / 0 FAIL**，与基线逐字一致（`--update` 只产生纯文案 DIFF）。

### ★★★ 本轮新增的两条硬教训
1. **判据直接取属性会让整个套件崩掉，比报红更危险。**
   D1c 初版写 `h.dialogue_ui._ai_pending is True` ⇒ 属性缺失抛 `AttributeError`
   ⇒ 套件**中途崩溃**，后面 130+ 条判据**一条不执行**；输出只是"截断"⇒ 极易被读成"挺绿"。
   ⇒ **判据读新增状态位一律 `getattr(x, 'k', None)`**。
2. **负控制变异体必须"精确复刻历史版"，不能"随便拆一处"。**
   N1（只拆 `__init__`）与 N2（只写回占位）**实测都不报红**：`_ai_thinking_on` 里的 `= True`
   会把属性**重新创建**、占位串**已不被产品读**。⇒ 只有**两处同降**才复现
   ⇒ 再次实证「多道防线须同拆才复现」。初版期望写"必须报红"是**判据侧的错**，已如实改为"断言不报红"。

★★ **变异锚点禁 `replace(old,new,1)` + 禁"全文唯一"假设**：
`self._ai_pending = False` 全文 **3** 处（注释里还有）⇒ 打在第一处**注释**上 = 静默失效
（负控制返 `[]`，看着像"防线结实"）。正解 = **先框函数体（缩进判边界）再在体内找**。
