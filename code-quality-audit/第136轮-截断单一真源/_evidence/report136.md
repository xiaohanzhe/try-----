## §2 病是什么

`ralsei_pet/src/main.py`（改前，`start_autonomous_speech._on_reply` 里）：

```python
for sep in ('\n', '。', '！', '？', '!', '?'):
    if sep in text:
        head = text.split(sep, 1)[0].strip()
        if head:
            text = head + ('' if sep == '\n' else sep)
        break
if len(text) > 40:
    text = text[:40]
```

而事件链用的是 `event_speech.first_sentence(text, 24)`。两者**从来就不是同一份实现**：

| | 自主开口（内联） | 事件链（`first_sentence`） |
|---|---|---|
| sep 顺序 | `\n` **优先** | 句号优先（第135轮改成"最靠前"） |
| 上限 | 40 | 24 |
| 短句保护 | **没有**（无 `MIN_FIRST_CHARS`） | 有（6 字） |
| 超长时的兜底 | 直接 `text[:40]` | 先找句末标点，找不到才硬截 |

而 `main.py` 14116 行（改前）的注释写的是「只保留第一句，避免模型长篇大论撑爆对话框」——
它**没说自己和事件链同源**，但第135轮我在 `first_sentence` 的 docstring 里写过"与那边同源"，
那句是**假断言**，第135轮已改正，本轮把那 8 行删掉，假断言从"改口"变成"不再需要"。

### 为什么内联那份一定会吊尾巴

`text[:40]` 是无条件的：只要截断点不在标点上，用户看到的就是半个句子。
真实样本（第131轮 `live7_131.jsonl`）：

```
raw : 听说被领导训了一顿？那天是什么情况呢？有没有遇到什么特别让人心烦的事？我在这边听着呢。
old : 听说被领导训了一顿？那天是什么情况呢？有没有遇到什么特别让人心烦的事？我在这边听   ← 40 字，断在"我在这边听"
new : 听说被领导训了一顿？那天是什么情况呢？有没有遇到什么特别让人心烦的事？              ← 35 字，完整
```

## §3 三路实测（`diag136.py` / `diag136c.py`）

**口径先说死**：真实语料 = **84 条**（第131轮真机 42 + 第133轮事件 42）。
`diag136.py` 跑的是 98 条 = 84 真实 + 14 条构造样本（覆盖边角）；
**下面的数是 84 条真实的**，构造样本会把平均分拉偏，不能混着报。

| 实现 | 吊尾巴 | 平均长度 |
|---|---|---|
| 旧内联 | **10 条** | 16.2 字 |
| `first_sentence(t, 40)` | 0 条 | 12.5 字 |
| `fit_sentences(t, 40)` | **0 条** | **18.6 字** |

逐条归因（`diag136c.txt` ②）：

- 旧内联 vs `first_sentence(t,40)`：**20 条**不同
  → 10 条"旧的吊尾巴、新的不吊"（**修复**）、9 条"旧的没吊、新的更短"（**砍掉后半句**）、1 条其余。
- `fit_sentences` vs `first_sentence`：**33 条**不同，其中 **32 条多留了一整句**，平均 **+6.2 字**。

### 这条数据推翻了"合并成一个函数"的方案

把 `first_sentence(t, 40)` 拿来做自主开口，吊尾巴确实归零，但**平均从 16.2 掉到 12.5 字** ——
砍掉的正是"追问一句 / 补一句在意"，而那恰恰是主动搭话里最像人的部分：

```
raw : 那你是因为什么事情被骂的呢？听起来挺让人不爽的……我在这边感觉不太舒服呢。
first: 那你是因为什么事情被骂的呢？                       ← 14 字
fit  : 那你是因为什么事情被骂的呢？听起来挺让人不爽的……我在这边感觉不太舒服呢。  ← 32 字
```

⇒ 两个函数要的东西**不一样**：

| 链 | 语义 | 上限 |
|---|---|---|
| 事件反应 `first_sentence` | **只要一句**（触觉反应不该是小作文） | 24 |
| 主动搭话 `fit_sentences` | **能说多少说多少，但必须说完整** | 40 |

## §4 产品改动

### 4.1 `event_speech.py`

1. **`_SENTENCE_ENDS` 加了 `…`**（原来按"句内停顿"排除）。
   依据是实测：加进去对事件链 **42 条真机回复 0 变动、3 条泄漏输出逐字不变、7 条既有契约全过**
   （`MIN_FIRST_CHARS` 兜住了）；而它在自主链上修掉一条真吊尾巴
   （「…叫豆豆是吧……我记得你有时候会给它点吃」被 40 字硬截切断）。
   `——` 仍不算：语料里只作插入语。
2. **新增 `_eat_sentence_end()`**：连续句末标点必须一起吃，

4. **新增 `AUTO_SPEAK_MAX_CHARS = 40`**：上限从 `main.py` 的魔法数收进模块 ——
   **截断长度必须单一真源**（第135轮 `EVENT_SPEAK_MAX_CHARS` 已是这么收的）。

## §7 判据自己翻的车（2 处）

### 7.1 `check136 E3`：负控制**没落进被测分支**

第一版：

```python
check("E1 `……` 不被切成单个 `…`", ES.fit_sentences('嗯，好吧……').endswith('……'))
check("E3 负控制：停掉 `_eat_sentence_end` 后 E1/E2 必须报红", ...)
```

结果 E3 **报红**：把 `_eat_sentence_end` 停成恒等之后，E1/E2 **照样成立**。

回查（`diag136b.py` → `diag136b2.txt`）才明白两件事：

- `fit_sentences('嗯，好吧……')` 全文 6 字 ≤ 40，走的是"整段就是 head"那条路，
  切点下标是谁都一样 ⇒ **那条断言恒真**；
- 更一般地：`fit_sentences` 挑的是 `ok[-1]`（最大下标），而连续标点的 run-final 下标最大
  ⇒ 只要 run-final 放得下就总是它被选中，"吃不吃完"不影响选择。
  **6 个上限 × 1250 条语料实测：40 / 24 上 0 条差异，只有 max ≤ 12 才出现。**

真正会变的是 `first_sentence`：它的句号分支挑"**第一个够长的**切点"，
若连续标点里靠前那个就已经够长，就会切在 run 中间 ⇒ 只剩一个 `…`。
真实语料上确实有 **3 条**差异，方向全是 **eat=on 保住 `……`**。

⇒ E 段改写：

| | 改前 | 改后 |
|---|---|---|
| E1 | `fit_sentences` 断言 `……`（**恒真**） | `first_sentence('真的很好呀……')`（真需要 eat） |
| E2 | 既有契约 `诶？！好舒服呀。` | 不变 |
| E3 | 负控制 | 改成**合同**：`fit_sentences` 输出不以单个 `…` 收尾（并注明它**不是** eat 的守卫） |
| E4 | — | 负控制：停掉 eat ⇒ 必须退化成 `真的很好呀…` |
| E5 | — | 恢复后 E1/E2 仍成立 |
| E6/E7 | — | 真实语料那 3 条：分母非空 + 停掉 eat 后 **3/3 全部退化** |

这一处值得记进教训本：**"合同"和"守卫"是两回事**。
一个断言恒真不等于它没价值（它仍能在别人改动时抓到破坏），
但**不能拿它当负控制的目标** —— 负控制要求"破坏后必须红"，恒真断言做不到。
