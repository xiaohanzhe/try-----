# 第173轮 · `obj_doorAny` 实例物化（把纸上的路网铺到地上）

> 仓库根：`try - 副本`；工程：`ralsei_pet/`

> 结论一句话：**172 轮画在纸上的 798 条 Any 门边，此前一条都没被消费；本轮把 820 个门实例真正写进场景，其中 801 条端到端解析出了目标场景。**

## 1 起点：路网有了，地上没铺

第172轮把 `obj_doorAny` 的每实例目标取证出来、落了 **798 条边**进 `_routes.json`
（全表 1,961 → 2,759）。当时收口时留了一句"路网已画在图上但还没铺到地上"——本轮就是去铺。

实测确认：**产品场景里 `src == 'obj_doorAny'` 的条目恒为 0**。
`item_interact.build_props()` 是靠遍历 `scene['objects']` 建可交互物的，
没有实例 ⇒ 没人调 `route_for_door()` ⇒ 798 条边**零消费方**。

### 1.1 根因不是"忘了写"

`gen_objects44.object()` 的规矩是：

> 查不到 sprite 帧 ⇒ 返回 `None`（不可见的纯逻辑锚点画出来是一堆空框）

而 `assets/scenes/objs/` 里 **没有 `spr_doorAny_0.png`** —— `spr_doorA ~ spr_doorF` 全都有，就缺它。
⇒ 881 条 Any 实例在生成 `objects` 时被**静默跳过**。这是一次典型的"素材缺失伪装成实现缺失"。

## 2 做法与结果

### 2.1 为什么不重跑生成器

第68轮 `gen_objects68.py` 会用 inst68 重建 `objects`，第117轮又改过门的尺寸。
重跑链上任何一环都会把后来几轮的增量冲掉（记忆 §130「派生字段必被重建冲掉」）。
⇒ 本轮只**幂等追加**缺失项，不动任何已有条目，也不动生成器本身。

代价：将来若有人重跑 `gen68`，这些条目会消失。
已用 `check173 D3`（反回滚闸）兜住——消失即报红，不会被静默吞掉。

### 2.2 产物字段

```json
{"pos": [x, y], "src": "obj_doorAny", "depth": 19000}
```

**故意不写 `sprite`**：原作 `obj_doorAny` 是 `visible=false` 的触发器，
`is_drawable_object()` 靠 `_obj_visible.json` 的 hidden 名单把它滤掉 ⇒ 永远不绘制。
给它写一个指向不存在文件的 sprite 才是假话。

### 2.3 四本账（`check173` A 段全部独立重算）

| 口径 | 条数 | 来源 |
|---|---|---|
| 原作侧实例表 | **881** | 第172轮 `analyze172.json`（跨轮锚定，不靠记忆） |
| 第42轮普查 | **830** | `inst42*` 五章（恰好已无重复坐标） |
| 已登记房间（= 本轮物化） | **820** | 830 按「有没有场景载体」二分 |
| 未登记房间（如实落空） | **10** | 7 个 `(章,房间)` 键，没有载体 |

逐章物化：`ch1 0 / ch2 26 / ch3 187 / ch4 361 / ch5 246` = **820**（ch1 原作本来就没有 Any 门）。

落盘面：**77 个场景文件**（30 个分片 + 47 个独立文件），`git status` 只多这两类。

### 2.4 端到端（`check173` C 段，`build_props` 实测，不是查源码猜的）

| 指标 | 数值 |
|---|---|
| 解析出目标场景 | **801 / 820**（97.7%） |

### 2.5 ★★★ 本轮最贵的一课：`_index.json` 与场景文件不齐

第一次跑注入器：**705 条**（不是 820），另有 **125 条**被算成"落在未登记房间"。

查出来的真因：

```
_index.json 登记 (章,房间) 对 = 2166
盘上场景容器里的 (章,房间) 对 = 2079
差 87 —— 而盘上 88 个独立场景文件里，正好 87 个没有 original_room_id
```

也就是说：那 87 间房**登记是登记了，但场景文件不自带房间号**，
注入器只认场景自带字段 ⇒ 整块跳过 ⇒ 115 条门白白落空。

修法：房间号**回退到 `_index.json`**。
依据是产品运行时本来就只读 index —— `main.py::_scene_rooms()` 第 4694~4698 行：

```python
_rid = sc.get('original_room_id')
if isinstance(_rid, int):
    room_of[str(scid)] = _rid
```

⇒ 注入器与运行时**同源**，行为一致；而且**不必**去改 87 个场景文件的 schema
（那会波及房间反查 / 卡片派生，本轮不碰）。

修完：`705 + 115 = 820`，剩 10 条属于真正没登记的 7 个房间。

> 附带发现（未修，留档）：这 87 个独立场景文件缺 `original_room_id` 本身是个数据缺口。
> 运行时靠 index 兜住了，所以**现在不疼**；但任何"只读场景文件"的新代码都会踩。

## 3 副线：E 盘坏区诊断与记忆库抢救

### 3.1 症状与判定

- `E:` 卷标「肖翰哲」，976 GB，**exFAT / 固定盘**；`Get-Volume` 报 **Healthy**、942 GB 空闲。
- 但写入性能异常：128 MB 顺序写 **E 25.3 MB/s**，同机对照 **D 1139 MB/s / C 1001 MB/s**（差 40~45 倍）。
- 卷根目录里有**手机完整体**痕迹（`Huawei/` `HuaweiSystem/` `Android/` `DCIM/` …）——
  与用户回忆「E 盘接过华为手机」吻合，是**手机写入过**的卷。
- 另有 `FOUND.000`（1 MB）＋ `FOUND.001`（**78 个 `FILE00xx.CHK` / 5.5 GB**，头部 `USBC\x10…`，非图片）。
  `FOUND.*` 是 chkdsk/卷修复留下的孤儿簇回收目录 ⇒ **这个卷历史上被修过、且修出过残骸**。

判定：不是"盘要坏了"，是**散落坏点**（坏块被驱动反复重试 ⇒ 表现为某个文件特别慢/挂死），
外加 5.5 GB 的 `FOUND.001` 残骸。

### 3.2 ★★★ 最贵教训：坏块上 `subprocess` 的超时是**假的**

`subprocess.run(..., timeout=10)` 在坏块上**实际卡了 9 分 20 秒**。

原因：`timeout` 到期后 `Popen.kill()` 只对**进程**下手，
而这时进程正卡在**内核态**（等着坏块的 SCSI 重试）。信号杀不掉内核态等待，
`run()` 又必须**等子进程真的被回收**才返回 ⇒ 超时形同虚设。

换线程更糟：线程**不可杀**，还会拖住解释器退出（主线程 join 不到它）。

结论：**用户态没有绕法**，只能卷层修（`chkdsk /f`）或绕开该卷。
⇒ 本轮定下的规矩：**成品→E / 临时与递归活→D**（见用户级 `MEMORY.md` 的盘务授权）。

### 3.3 抢救结果

记忆库 `E:\RalseiMemory\`（`data_store` 的唯一 vault）逐文件抢救（`copytree` 会在
`cache\jieba.cache.old` 上挂死，改成逐文件 + 单文件超时跳过）：

- **80 个文件 / 13.2 MB 全部救回**，无一个读取失败。
- 已复制到 D 盘备份；原 vault **保持不动**（记忆契约：迁移只复制）。

### 3.4 未完成：`chkdsk /f`

提权通道被封（`admin=False`；安全策略拦截 `Start-Process ... -Verb RunAs`，
提示 "bypasses validation"）⇒ **需要用户手动执行**：

```
chkdsk E: /f
```

跑完复检的 8 个坏点清单见 `.workbuddy/memory/参考-契约与历轮（详版）.md` §174.3。

### 4.4 本轮判据自己踩的坑（逐条留档）

1. **★★★ M3 改了三版才真正落进 B3 的分支**
