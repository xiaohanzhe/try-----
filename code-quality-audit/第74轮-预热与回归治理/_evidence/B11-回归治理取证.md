## 1. 事故：探针 v1 把日志打死了 ⇒ 7 个假问题

### 1.1 现象

用 v1 时钟注入器（±115200s）跑 7 个套件，全部报 DIFF。
但**看 DIFF 内容**，不是断言变了 —— 是**所有日志行凭空消失**：

```
--- s1_anim_miss (baseline)
+++ s1_anim_miss (now)
-<TS> [INFO] ralsei_pet.sprite_loader — [anim-config] 已从 animations.json 加载 114 组动画（legacy 28 组，schema=1）
-<TS> [WARNING] ralsei_pet.sprite_loader — [anim-miss] 动画名不存在: 'no_such_anim' → 回退 '...'
 ...（几十行 [PASS] 一条没动）
```
`round34_store_config` 更夸张：baseline 里 10 行 `已清理过期配置备份` 全没了。
**PASS/FAIL 计数一个没变**（合计 279 / 0）。

### 1.2 根因（不是套件的问题）

v1 把 `time.localtime` 换成了**普通函数**（lambda）：

```python
_time_mod.localtime = lambda s=None: _rl(_shifted_now() if s is None else s + _OFF)
```

而 `logging.Formatter.converter = time.localtime` 是**类属性**，
`Formatter.formatTime` 里写的是 `ct = self.converter(record.created)` ——
普通函数会被**描述符协议绑定**，Python 把 `self` 一起塞进去：

```
File "C:\Python311\Lib\logging\__init__.py", line 624, in formatTime
    ct = self.converter(record.created)
TypeError: <lambda>() takes from 0 to 1 positional arguments but 2 were given
```

`StreamHandler.emit()` 自己把这个异常吃掉了并转交 `handleError(record)`；
而本项目**第54轮**刚把 `_SafeEmitStreamHandler.handleError` 改成**静默计数**
（不再往 stderr 喷 `--- Logging error ---`+Traceback）……

⇒ **异常被静默吞掉，所有日志消失，屏幕上一条报错都没有。**

> 这条链值得单独记住：**上一轮为了让用户不被 Traceback 骚扰而做的"静默"，
> 把这一轮的探针故障变成了"没有任何征兆的输出缺失"**。
> 静默兜底是好事，但它会让"故障"退化成"内容变少" —— 所以**兜底必须留计数器并可被查**
> （`emit_failures`，本事故就是靠它定性的）。

### 1.3 修复

v2 把替换值一律改成**可调用对象（实例）** —— 实例没有 `__get__`，
属性查找不会绑定实例，描述符问题从根上消失。见 `_tools/clock_shift/sitecustomize.py`。

### 1.4 修复后：7 个套件在 ±32h 下**全部 IDENTICAL**

```
s1_anim_miss 0 17 0 IDENTICAL / s2_anim_json 0 40 0 IDENTICAL / s3_alias_legacy 0 19 0 IDENTICAL
round9_memory 0 51 0 IDENTICAL / round34_store_config 0 17 0 IDENTICAL
dialog_lounge52 0 82 0 IDENTICAL / sit_round54 0 53 0 IDENTICAL
合计：PASS=279 FAIL=0  套件=7     （+115200 与 -115200 两档均如此）
```

## 2. 真·时钟耦合：只有 `round12_store`（已修，且**改前后都实测过**）

### 2.1 症状（改前，用 v1 跑出来的 FAIL 是**真的**）

第一节那批是假的，但 `round12_store` 的失败是真的 —— 因为它的断言本身拿
`time.time()` 当基准去 `utime()`，而 **OS 赋的 mtime 走真实时钟**：

```python
os.utime(_vlt/'config.json', (time.time()-3600, time.time()-3600))   # 想让 vault 显得更旧
```

**实测（把改前的原版从 git 取出来跑，cwd 放回它自己的目录）：**

| 时钟 | 结果 |
|---|---|
| 不平移 | **58 PASS / 0 FAIL** |
| **+115200s** | **56 PASS / 2 FAIL**（`B13` 两边同名时留新的 / `B19` 源比目标旧 → 目标胜出） |
| −115200s | 58 PASS / 0 FAIL |

原因：+32h 时 `time.time()-3600` 得到的是"未来 31 小时"，`utime` 照写 ⇒
vault 反而变成**更新**的那一份 ⇒ "留新的"判据方向反过来 ⇒ FAIL。
（这解释了为什么只有**正向**平移才炸。）

### 2.2 修法

基准换成**文件自身的 mtime**（不再问"现在几点"）：

```python
_vlt_t = os.path.getmtime(os.path.join(_vlt, 'config.json'))
os.utime(os.path.join(_vlt, 'config.json'), (_vlt_t - 3600, _vlt_t - 3600))
```

**实测（改后）：±115200 两档均 58 PASS / 0 FAIL。**
⇒ 这不是"把判据改松"，是**把参照系从"墙上时钟"换成"被测文件自己"**，判据反而更严。

## 3. 事故二：判据口径错 ⇒ "5 个非密闭套件"也是假问题

### 3.1 现象

第一版 `audit_env_leak74.py` 直接扫 `_out/<id>.txt`（**原始**输出），
报出 19 个套件"泄漏真实环境"，`C:\Users\23002\AppData\Local\Temp\...` 满屏。

### 3.2 根因

**扫错了文本**。进比对的是 `normalize()` **之后**的文本 —— 那些临时目录路径
早就被 `_TMPDIR` 换成 `<TMP>` 了，基线里根本没有。
拿原始文本当判据 = 又一个"判据口径不对"的假问题。

### 3.3 修法

脚本改成**直接 import `run_all` 调它自己的 `normalize()`**（单一真源，不重写一份）。
重扫（归一化后、与基线同口径）：

- `npc_persona55` / `npc_place56` / `round8_anim` / `soul_round55` / `model_conc57`
  —— **全部干净**（它们在原始文本里出现的临时路径 100% 被归一化）。
- 唯一残留的绝对路径是 `C:/Python311/python.exe`（run_all/seed runner 自己打的解释器行，
  每轮恒定，**不造成漂移**）。
- ⇒ **"5 个非密闭套件"里 4 个是假问题。**

## 4. 真·非密闭：`check73`（唯一真缺陷，已修）

### 4.1 证据：真实保管库路径**活到了比对文本里**

`_out/check73.baseline.txt`（归一化后，即基线本身）：

```
<TS> [INFO] ralsei_pet.main — NPC 系统就绪：登记 96 个（主线 78 / 纯 NPC 18）；人设 76 份；
     点名别名 196 条；记忆落盘=E:/RalseiMemory/npc_memory
```

### 4.2 根因：注释写的是假话，而且**是构造顺序问题**

`run_all.py` 的 SUITES 注释与 `check73.py` 自己都写着
「隔离内存记忆，**绝不碰**用户 `E:\RalseiMemory` 保管库」。实测**不成立**：

```python
_pet = M.RalseiPet()                       # ← 第571行：构造期就已解析并建了**真实**保管库
...
_pet.npc_memory = NP.MiniMemory(root=None) # ← 第585行：构造**之后**才换后端，为时已晚
```

两个后果（都是 run_all 文档里写明的"不隔离的后果"）：
① **基线不封闭**：输出随"E 盘在不在线""E 盘上有没有 memory.json"漂移；
② **跑一次就往用户真实保管库写东西**（构造期那一下就写了）。

### 4.3 修法

把 `check73` 补进 `run_all.HERMETIC_IDS`（注入 `RALSEI_MEMORY_DIR`
⇒ `memory_store.find_device_dir()` 直接 return，**那才是真正管用的隔离层**），
并把 SUITES 注释与 `check73.py` 里那两处假话**逐条更正**（不许留言）。

### 4.4 基线重建前的 DIFF（**逐条看过才更新**）

更新前后 **PASS=85 / FAIL=0 一条没变**，变的只有日志：

```
-<TS> ... 记忆落盘=E:/RalseiMemory/npc_memory        ← 真实保管库（基线不封闭的铁证）
+<TS> ... 记忆落盘=<TMP>
+<TS> ... 已把历史数据收编进最终存储: <ROOT>/ralsei_pet/config.json -> <TMP>
+<TS> ... 新位置无记忆，已从旧版 memory.json 继承: <ROOT>/ralsei_pet/modules/../memory.json
+<TS> ... 保温看门狗已启动：keep_alive=30m（只在模型"新载入"时设一次）
-<TS> ... 幽灵：接触时长已读回 接触=<DUR> 决心=0.000 档位=dim
```

★ 新增的三行正是 run_all 文档预言的症状："隔离后新位置一定为空 ⇒ 收编/继承**必然发生**"。
⇒ 旧基线确实**随 E 盘状态漂移**，这次更新是**从"不封闭"修成"封闭"**，不是改判据。

## 7. 教训（本轮沉淀）

1. **探针要先自检再下结论**。v1 没自检 ⇒ 7 个假问题。现在自带 6 条 A/B 锚点，
   其中 A1 特意用**另一个进程**取真实时钟（同进程比较是自说自话）。
2. **DIFF 必看，而且要看到"变了什么类型的行"**。7 个假 DIFF 全是"日志行消失"，
   PASS 计数一条没动 —— 这个形状本身就该报警：**断言没变，只可能是输出侧出了问题**。
3. **判据口径要写清楚在哪份文本上判**（原始 vs 归一化）。差一步就是 19 个 vs 1 个。
4. **静默兜底必须留可查的计数器**。`handleError` 静默是上一轮的正确决定，
   但它让本轮的故障表现成"内容变少"而非"报错"；`emit_failures` 是唯一线索。
5. **注释里的"绝不…"必须能被实测证伪**。`check73` 那两处假话存在了整整一轮，
   正是靠"扫描真实路径是否活到比对文本"这条外部判据抓出来的。
