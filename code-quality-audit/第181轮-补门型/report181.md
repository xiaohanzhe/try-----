## 1. ★★★ 先纠账：之前记的「已接线 25 种门型」是假的

上一轮（也是我记在脑子里的口径）写着「Deltarune 侧已接线 25 种门型」。这一轮一查，**不成立**：

```
_routes.json 共 2,768 条（本轮之前）
按 when_scene 的世界前缀拆开：
  ch1..ch5（Deltarune）  1,610
  ut                       525
  oneshot                  420
  outertale                209
  desktop                    4
```

`via` 字段里混进了 UT / outertale 的**同名门**（`obj_door_t` / `obj_door_u` / `obj_door_w` /
`obj_door_v` / `obj_door_ruins13` / `obj_papdoor` / `obj_demodoorA` …），
其中 `obj_door_w` 归一化之后与 Deltarune 的 `obj_doorW` **撞车**。

还有一类更直接的假象：

```
via 里写着  obj_doorAmusicfade / obj_doorBmusicfade / obj_doorCmusicfade / obj_doorDmusicfade
实例表里查  0 命中
真名是      obj_doorX_musfade
```

**结论**：归一化字符串是不够的，**必须按世界分离**。按世界拆开重算之后，
Deltarune 侧带原件依据的门型只有 **9 种**，另有 **443 条** `via`/`when_src`/`kind` 全空
（早轮手写的）。而 `obj_doorA`（204 个实例）/ `obj_doorB`（210）/ `obj_doorC`（54）
在 Deltarune 侧**零接线** —— 它们一直在被 UT 的同名门"冒充"。

这一条是本轮最值钱的发现，也是"补门型"这件事必须现在做的原因。

## 2. 门机制（五章一致，`gml_Object_<obj>_Alarm_2`）

| 门对象 | `Alarm_2` 做的事 | 位移 |
|---|---|---|
| `obj_doorA` / `obj_doorA_musfade` | `room_goto_next()` | **+1** |
| `obj_doorB` / `obj_doorB_musfade` | `room_goto_previous()` | **−1** |
| `obj_doorC` / `obj_doorC_musfade` | `room_goto(room_next(room_next(room)))` | **+2** |
| `obj_doorD` / `obj_doorD_musfade` | `room_goto(room_previous(room_previous(room)))` | **−2** |
| `obj_doorE` | `room_next` 叠**三**次 | **+3** |
| `obj_doorF` | `room_previous` 叠**三**次 | **−3** |
| `obj_climb_door` | 实例 `PreCreate` 写 `doorRoom` → `Alarm_2` 做 `room_goto(doorRoom)` | 逐实例 |

`musfade` 变体与普通版**逐指令相同**（只多一个音乐淡出）。位移落在 `Data.Rooms` 的**下标**上
（`_room_order.json` 的 `meta` 早就写明），所以：

- **B2** 用下标算并独立重推，**B3** 拿原始指令（`probe181.ch*.txt` 的 Push/Call）另算一遍，
  **B6** 拿 `_room_order.json` 反查房名 —— 三条互相交叉，任何一条口径歪了都会红。
- **B4** 断言 `src_room_id + shift == dst_room_id`（覆盖项除外）。
- D 门 61 个实例里，**58 条**推出的落点与既有路由完全吻合 ⇒ 位移模型站得住。

## 3. ★★★ 三处口径，故意不按直觉写

### ① `when_door` 取**门名字母**，不是 `entrance` 数值

```
ch1 的 entrance：C=4  D=5  E=6  F=7
ch2 起         ：C=3  D=4
```

同一个字母在两章里的 `entrance` 值不同，所以它**不能当常量**。
`when_door` 沿用既有 1,200+ 条的老口径 = **名字字母**。
`B8` 就是"用 `entrance` 数值填了字母"的抓捕器（变异 M4 实测：把 `'E'` 改成 `'6'` ⇒ 当场红）。

### ② 全五章 A~F 只有**一处**单点覆盖

```gml
// ch3 · gml_Object_obj_doorC_Alarm_2
if (global.chapter == 3 && room == 110) { room_goto(28); exit; }
```

`110 + 2 = 112` 才是位移的自然结果，但原作在 ch3 的 110 房跳 **28**。
`B5` 把这件事钉成"**唯一一处** override，且必须是 `(ch3, 110, 28)`" —— 多一处、少一处都红。

### ③ 落边只按 `(源, 目标)` 去重 ⇒ 落边实例 64 ≠ 唯一边 63

同房两扇同型门可能指向同一间。所以：

- **唯一边 = 63**（`A2` 钉死）
- **落边实例 = 64**（`D1` 的分子）
- 差额 1 条被多实例共用 ⇒ `D2` 逐条点名（不是"算不齐"）

## 5. ★★★ 归因闭合：610 个实例，一个都不许漏

三类归因各自带得出证据（`D3`/`D4`/`D5`）：

## 7. 隐藏房：只登记，不动机制（按你的裁定拆两轮）

原作有一批**概率出现**的隐藏房（`man` 房），机制都是 `ceil(random(50)) == 50`（**1/50**），
而且有"进过一次就锁"的全局 flag。本轮**只登记数据**，写进 `_routes.json` 的新顶层键
`_hidden_rooms`（4 条），**没有任何一条标 `enabled`**（`E4` 钉死）——机制留到第 182 轮。

| 场景 | 概率 | 状态 | 为什么 |
|---|---|---|---|
| ch1 森林·man | 0.02 | `target_not_registered` | 原作确有这扇门（`room_forest_area5` 里），但 `room_man` **没登记成场景** ⇒ 只能存证据 |
| ch2 赛博都市·man | 0.02 | `data_only` | 现有表把这扇门记成**确定性边**（priority 7122），与原作 1/50 不符 —— 本轮**不改既有边** |
| ch3 `dw_ch3_man` | — | `no_incoming_edge` | 场景已登记，但**零入边**；本轮五章 door 代码里没找到指向它的门 ⇒ 条件**未解**，不臆造 |
| ch4 `dw_churchb_man` | — | `gate_unresolved` | 入边是 `obj_doorAny`，实例 `PreCreate` **无条件**写 `doorRoom`；概率/前置条件不在门代码里 ⇒ **未解** |
