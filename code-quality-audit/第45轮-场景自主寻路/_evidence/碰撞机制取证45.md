# 第 45 轮续 · 原作「障碍物阻挡」机制取证

> 目的：回答用户「**注意有些场景里是有障碍物的，别把那些障碍物的阻挡效果变没了，
> 简而言之就是交互效果和原作一样**」——即先弄清原作到底怎么实现阻挡。
>
> 方法：UTMT CLI v0.9.2.0 反汇编 ch1 `data.win`（147 间房 / 1680 code / 353 GameObject）。
> 原始证据：本目录 `collide45.txt` `collideF45.txt` `collideG45.txt` `collideH45b.txt` `collideI45.txt`。

---

## 结论 1：原作**不用** `solid` 属性

```
GameObjects 总数 = 353 ; Solid=True 数 = 0
```

353 个对象里 **没有一个** 把 `Solid` 设为 True。所以「原作用 solid 属性挡路」是**错误假设**，
按这个假设去实现会与原作不符。（这正是「判据报红先怀疑判据」的同型：假设本身没验过。）

## 结论 2：阻挡 = **`place_meeting` 对 `obj_solidblock` / `obj_interactablesolid` 的判定**

主角移动代码 `gml_Object_obj_mainchara_Step_0`（**1874 条指令**）里：

| 函数 | 次数 |
|---|---|
| `collision_rectangle` | 18 |
| `place_meeting` | 12 |
| `collision_line` | 2 |

12 次 `place_meeting` 的第 3 参数（对象 id，**从右往左压栈**）实测：

| 指令位 | 移动方向 | 对象 id | 对象名 |
|---|---|---|---|
| 372 | 左移 | `17` | `obj_solidblock` |
| 392/393 | 右移 | `17`,`18` | `obj_solidblock`, `obj_interactablesolid` |
| 424/425 | 上移 | `17`,`18` | 同上 |
| 464/465 | 下移 | `17` | `obj_solidblock` |
| 613/614 | 下探(循环) | `17` | `obj_solidblock` |

（`obj_interactablesolid` 的 **parent = `obj_solidblock`**，所以判 `obj_solidblock`
在 GM 里会**连带命中** `obj_interactablesolid`/`obj_soliddark`/`obj_solidlong`/`obj_pushableblock`。）

> ⚠️ 参数顺序：GMS2 实参**从右往左压栈** ⇒ 反汇编里最后一个 push 的对象 id 才是**第 3 参**。
> 这是第 43 轮就踩过并记录在案的坑，本次已按此解读。

## 结论 3：障碍物的几何 = **自由摆放的缩放矩形（20×20 基准）**

```
obj_solidblock         sprite=spr_solidsmall  20x20  bbox=Circle  visible=False
obj_interactablesolid  sprite=spr_interactable 20x20  bbox=Circle  parent=obj_solidblock
obj_soliddark          sprite=spr_soliddark   40x40  parent=obj_solidblock
obj_solidlong          sprite=spr_solidlong   20x20  parent=obj_solidblock
obj_pushableblock      sprite=spr_npc_block   20x20  parent=obj_interactablesolid
obj_mainchara          sprite=spr_krisd       19x38  bbox=Circle   ← 主角
```

实例样本（`room_krishallway`，540×240）：

```
obj_solidblock  x=61  y=109  xs=11.05 ys=0.90   ← 220×18 的墙
obj_solidblock  x=40  y=108  xs=1.00  ys=3.45   ←  20×69 的柱
obj_solidblock  x=172 y=114  xs=2.60  ys=1.00   ←  52×20 的台
```

**⇒ 障碍不是 20×20 网格对齐的**（x=61/457/479/40/172… 是任意像素 + 小数缩放）。
要「交互效果和原作一样」，必须**逐实例矩形**，不能用瓦片网格近似。

## 结论 4：障碍数据 **可以从房间里直接导出**

用正确的路径（`layer.InstancesData.Instances` + `inst.ObjectDefinition`，
**不是** `room.GameObjects` / `layer.Instances` —— 第 44 轮连踩两次的坑）：

```
ch1 房间总数 = 147
含障碍实例的房间数 = 125 ; 障碍实例总数 = 1599
例：room_krishallway=9, room_town_north=22, room_town_mid=33, room_town_church=21,
    room_dark2=34, room_dark7=22, room_torhouse=12(+solidlong 1)
```

⇒ **数据可得，规模可控**（ch1 1,599 个；五章外推约 8k~10k 量级，待实测）。

## 对实施的指导

1. **障碍数据落地**：新增 `assets/scenes/_obstacles.ch<N>.json`，逐房间存
   `[{x,y,w,h,kind}]`，`w = round(20*xs)`、`h = round(20*ys)`。
   ⇒ 蒸馏进仓库（不用「用后即删」的临时区，回归锁才能依赖）。
2. **行走碰撞**：Ralsei 位移前，对**候选位置**做「20×20 缩放矩形 vs 19×38 主角」的
   矩形重叠检测；命中则**沿轴滑行**（原作的 `place_meeting` 是分轴判定 ⇒ 贴墙滑行是原作行为）。
3. **自然路线**：当前 `main.py` 移动是「直线奔向 target_pos」⇒ 直角折。要改为
   **贝塞尔/样条平滑 + 局部避障**：先算平滑航点，再对每段做障碍推开。
4. **交互一致性**：`obj_interactablesolid` 撞到会触发对话（`event_user(20)`）⇒
   桌宠撞到「可交互障碍」应触发短反应，而不是硬穿过去。
