## 3. 原作机制（第181轮取证，本轮直接引用）

```
ch1  obj_doorX_musfade.Alarm_2
     if (room == room_forest_area5) {
         ch = ceil(random(50));
         if (ch == 50 && global.flag[910] == 0) room_goto(room_man);
         else                                    room_goto(room_forest_starwalker);
     }

ch2  obj_doorw_musfade.Alarm_2
     man_room = scr_sideb_get_phase() == 0 && global.flag[917] < 2
                && global.flag[918] == 0 && ceil(random(50)) == 50;
     if (man_room) room_goto(room_dw_city_man);
     else          room_goto(room_dw_city_moss);
```

两条结论决定了实现形状：

1. **掷骰的主语是"你正站着的那间房"**（`room == room_xxx`），不是"原本要去哪"。
   ⇒ 触发点放在**出发**，不在"到达后"。
2. **概率是数据，不是代码**。`0.02` 写在 `_hidden_rooms[].probability` 里，
   代码只负责"用这个数掷一次"。

## 5. 三处口径（写错就白干）

### ① 掷骰的主语是 `from_scene`

原作条件是 `room == room_xxx`，那个 `room` 是**正站着**的房间。
判据 `B7` 钉死：站在**别的**房间掷骰一律不中。

### ② `match()` 一个字没动

`scene_routing.match()` 至今**零调用方** —— 真正换房走
`travel_to_scene → _resolve_travel_target → scene.switch()`。
而它的「按 `(priority, -score, 声明序)` 完全确定性」被 **20+ 个老判据**依赖。

⇒ 上一轮计划里写的"给 `match()` 加加权挑选"**作废**。把随机塞进去等于同时坏两件事：
既碰不到真实路径，又破坏一个被大量依赖的性质。

### ③ "掷中" ≠ "已发现"

`switch` 可能失败、过渡可能被用户取消。如果掷中就记账，会出现：
**没去成的那间房被记成"已发现"⇒ 那扇门永远消失，而且不报错**。
这是本项目最忌讳的"静默降级"。

⇒ `_commit_hidden_seen()` 先判 `cur != sid` 就直接返回 `False`，不写盘。
判据 `C3` 用 AST 钉这条提前返回**必须存在**。

## 9. 本轮踩的坑（全是判据/夹具自己的错）

### ① `all(bool)` —— 一行写崩

第一版 `C1` 写成 `all(not _res or min(_div) < min(_res))`，`all()` 收到的是 bool
⇒ `TypeError`，整段 C 段跑不起来。改成三个独立条件用 `and` 连。

### ② 锚点写 `\n`，源文件是 CRLF ⇒ 5 条变异**一条都没命中**

`mutate182.py` 第一版直接 `read()`（`newline=''` 保留 `\r\n`），而锚点里写的是 `\n`
⇒ 替换全部落空，表现像"判据不灵"。
修法：变异器读入时统一转 LF（**只写副本**，不碰被测物），并在注释里写明为什么可以这么做。

### ③ 变异时顺手删了逗号 ⇒ JSON 非法 ⇒ check182 在 `jload` 崩掉

`04_once_false` 第一版把
`"once": true,\n "status": "data_only",` 换成 `"once": false,\n "status": "data_only"`
—— **逗号被吃掉了**。

结果：`rc=1`，但**一条 `[FAIL]` 都打不出来**（崩在解析 JSON 那一步）。
这正是第178轮 M3 那个"看着抓到了、其实什么都没证明"的同款假象。

⇒ 变异器改为断言「红的条数 **> 0 且 < 总数**」：
只有 rc 非零、红项为空的那种，一律不算抓到。

### ④ `D4` 扫到了自己的说明文字

第一版正则 `[D-E]:[\\/]{1,2}[^'"\s]{0,20}` 把判据自己描述里的 `D:\` 当成硬编码路径
⇒ 假红。收紧成"盘符 + 真实首字符 + 至少 2 字符"。

### ⑤ `D5` 条数我数错了

第一版写 `== 27`，实际 28（A 5 + B0 1 + B 11 + C 6 + D 5）。
`D5` 执行到那一刻 `_n` 里还没有自己，所以判据是 `_n['p']+_n['f']+1 == 28`。

## 11. 一条**没有照字面执行**的决定（必须写明）

用户对「ch2 那条 `priority=7122` 的确定性边（`traffic_3 → dw_city_man`）」选的是
**「照原作改：7122 改指 moss」**。

实际查数据后发现：**`traffic_3` 的 W 门本来就有三条同源边** ——
`7121 → dog_traffic`、`7122 → man`、`7123 → moss`，三条 `when_*` 完全一样。
所以"把 7122 改指 moss"只会造出**第二条一模一样的 moss 边**（7123 已经是 moss）。

而删掉 7122 会同时撞两道老锁：

- `check181 A1`（路由总数 `>= 2831`，"只增不减"）；
- `check181 D1`（`610` 个实例的五分类闭合，"老账已覆盖"会从 528 掉到 527）。

⇒ **本轮没动这条边**，只在 `_hidden_rooms[1].note` 里如实写明现状。三点补充：

1. **不影响行为**：`7121` 优先级更小 ⇒ `match()` 永远返回 `7121`，`7122` **从未被消费**；
2. **不影响本轮目标**：隐藏房现在只能由 1/50 进去，这是本轮要的语义；
3. **它是 169 的建模遗留**：一扇物理门有三个互斥分支，却被记成三条无条件边 ——
   这是"分支条件没落进账本"，不是概率问题，属于 169 的口径，本轮不擅自扩大范围。

**要不要真删，等用户定。** 若删，需要按"引账不调数"同步改 `check181` 的 A1 与 D1
（给 D1 加第 6 类"概率覆盖"），那是另一轮的活。
