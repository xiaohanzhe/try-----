## 一、★ 第一件事：这条需求**原作没有**（必须诚实标注）

第46轮取证已确认：原作的"跟随"是**毛毛虫（caterpillar）**，方向是

```
主角 (obj_mainchara)  ——带路——>  队友 (obj_caterpillarchara)
parent = obj_mainchara;  target = 12 + slot*12
```

即 **主角走，队友跟**。原作里：

| 事实 | 出处 |
|---|---|
| 跟随目标恒为主角 | `obj_caterpillarchara.Create_0`：`parent = obj_mainchara;` |
| 走主角走过的路（25 帧历史） | `remx[25] / remy[25] / facing[25]` |
| 滞后帧数 | `scr_makecaterpillar`：`target = 12 + (slot * 12)` |
| 队伍 = 2 个队友位 | `scr_setparty(arg0, arg1)` |

★ **原作没有「灵魂」这个可被带领的实体** —— 原作里 `obj_heart` 是**战斗/弹幕里的
红心**，只在战斗界面出现，不是"跟着你走路的同伴"。
本项目的"灵魂"（`soul_entity`）是**桌面实体**，可以自由穿行场景（第76轮 R2/R3/R4 已落地）。

⇒ **R6 是本项目扩展**：把一个"桌面实体"交给某个 NPC 带领。
⇒ 但**机制照抄原作**：复用毛毛虫的**轨迹延迟采样**（`Companion.trace` + `sample_at`），
   只把"带路者"从 `obj_mainchara` 换成**被请求的 NPC**。

> ⚠️ 报告与代码注释里**不许写"原作就是这样"** —— 只有"机制照抄毛毛虫，
>    方向与原作相反（原作是队友跟主角，这里是角色带灵魂）"。

## 二、与 R5 的关系（正交，可共存）

| | R5 附身 | R6 带路 |
|---|---|---|
| 方向键归谁 | **角色**（用户操控 NPC） | **灵魂**（用户仍操控灵魂） |
| 谁在动 | 用户直接推着角色走 | 角色带路，灵魂被牵引 |
| 状态机 | `PossessionState` | `EscortState`（本轮） |
| 同意机制 | `ConsentState` 三态（Niko 需同意） | **复用同一套**（请求也要同意） |
| 锁关系 | 附身期间不建 escort | 带路期间不建 possession |

★★ **两者互斥**（都是"控制权"的重新分配）⇒ 必须显式裁决：
- 附身开始时 ⇒ **自动解除带路**（否则"角色被附身"与"角色在带路"冲突）；
- 带路开始时 ⇒ 不能处于附身态（`request` 里拒绝）。
这个互斥**必须落成判据**（否则会出现"两个状态机都说自己在管方向键"）。

## 三、`EscortState` 状态机设计

### 3.1 三态（与 `ConsentState` 同源的"状态少一档"教训）

```python
ESCORT_NONE  = 'none'      # 没在带路
ESCORT_ASKING = 'asking'   # 已请求，等对方同意
ESCORT_LEADING = 'leading' # 正在带路
```

★ 为什么"请求中"要独立一态：与 R5 同理由 —— 布尔两态会把"还没问"和"问过被拒"
合并，于是"再请求一次"永远触发不了。

### 3.2 追随者的移动 = **照抄毛毛虫的滞后采样**（★ 用户裁定：完全照原作）

```
被请求的角色（leader）每帧把自己的位置压进轨迹
灵魂（follower）取「滞后 lag 帧」那一点，**直接置位**
```

★★★ **用户裁定（2026-10-03，逐字）**：「**完全照原作（直接置位）**」

⇒ 即：灵魂位置 = `leader.trace[-（lag+1）]`，**不做"远处走过来"的中间态**。
- 好处：与原作 `obj_caterpillarchara` **完全同形**（`c.x, c.y = pt.x, pt.y`），
  "照抄"这条声明**没有折扣**；
- 用户**知情**瞬移这一点（选项里写明了"灵魂会从当前位置瞬移过去"）⇒ 这是**明确裁决**，
  不是我漏做了什么。
- ⚠️ 因此**不引入** `FOLLOW_NEAR_THRESHOLD` 之类的自创常量 —— 少一个自创数
  就少一处"照抄声明打折"的地方。

### 3.3 带路者**不寻路**（本轮边界）

R6 的"带路"**只做"跟着某人走"**，**不做"去某地"**：
- 角色自己怎么走（自主生活 `npc_roam` / 用户操控 / 其它）不归本轮管；
- 灵魂跟着角色的**实际轨迹**走（轨迹采样天然不会穿墙，因为轨迹是角色走出来的）。

★ 为什么这样切：用户的 R6 是"**请求角色带灵魂走**"（跟着人走），
而"请求角色**带我去某地**"是 R1/R7 那一层的事（涉及寻路，`scene_pathfind` 已在位）。
本轮**不抢跑**，把"带路 = 跟随某个具体角色"做扎实。

## 四、请求的入口与同意

### 4.1 入口键位（★ 用户裁定：新增 G 键）

★★★ **用户裁定（2026-10-03，逐字）**：「**新增 G 键**」

⇒ **G 键专用于"请求带路"**，与 Z（R5 附身）**完全分开**：
- Z = 附身 / 解除（已有，`check82` 守着，本轮**不动它**）；
- G = 请求身边角色带路 / 再按 G = 结束带路。

★ 为什么这是好裁决（原本我倾向复用 Z）：
- Z 复用会让"按 Z 到底会附身还是请求带路"依赖**隐藏状态**（有没有可附身目标），
  用户无法预测 —— 而独立键位**所见即所得**；
- 本项目 R 系列每个功能一个键（方向键 / Z / E / S），G 与既有键位不冲突；
- ⇒ 顺带让**回归锁更好写**：`check83` 可以断言"G 与 Z 走的是两条独立分支"，
  而不用断言"Z 内部的隐式退化"（后者是典型的"判据过窄/过宽"高发区）。

键位注册纪律（本项目硬规矩）：**绝不注册裸键** ⇒ 必须走既有的热键/按键分发通道，
并与 `S` 菜单、方向键、Z 的消费顺序**显式排好优先级**。

### 4.2 同意机制 = **复用 R5 的 `ConsentState`**

| 角色 | R5 附身 | R6 带路 |
|---|---|---|
| `kris` | DIRECT（可直接） | DIRECT |
| `ut_frisk` | DIRECT | DIRECT |
| `os_niko` | CONSENT（需同意） | CONSENT |
| 其余 | FORBIDDEN | FORBIDDEN |

★ **同一张 `POSSESSION_KINDS` 表**（单一真源）—— 不另建一张"谁能带路"的表，
否则两张表迟早分叉（本项目"同一份规则两处算"是最贵的坑）。
