## 2. ★★★ 这一轮真正难的不是"撤"，是"别把叫停听成再派一次"

「别让苏西去 oneshot 了」这句话里**同时**有：

| 要素 | 值 |
|---|---|
| 角色名 | 苏西 |
| 意图词（`ERRAND_INTENT_VERBS`） | **让** |
| 地点（`ERRAND_PLACE_ALIASES`） | oneshot |

⇒ `_errand_parse_intent` **原样命中** = 派活。
而 `ErrandBoard.assign` 对**同一个** NPC 是**覆盖**语义 ⇒ 表面上无声无息，
实际把人**重新上路**了（刚刚答应你要回来的那个人，又走了）。

所以这道口子需要**两道闸**，缺一不可：

1. **取消先于派活**：`handle_errand_command` 里先问"这是不是在叫停"，
   是 ⇒ 撤 + 回应 + `return True`（**不往下走**）。
2. **否定句不派**（`ERRAND_NEGATIONS`）：连"他没在办、所以取消不了"的那种句子
   也不会掉进派活里 —— 否则用户说"别让苏西去"，结果苏西真去了，这才是最糟的。

★ 代价已登记：否定闸是**整句从严**（「别客气，让苏西去 oneshot 吧」也会被当普通聊天）。
理由是做"离意图词多近"的精细判需要分词，而 `isalnum()` 对 CJK 也是 `True`（第147轮的坑）
⇒ **漏判无害，误派有害**。

## 3. 三条不变式（都在判据里钉死，别改）

### ① 作废 ≠ 办完

`abort()` 只弹 `_active`，**不进 `done`、不留 `result`**；
记忆走 `_npc_errand_note`（"还没办完就被叫回来了"），**不走** `_npc_errand_commit`。

> 为什么这么较真：`result_of()` 是"他办成的结果"。作废也写一条结果进去，
> 下次有人问他"上次那件事呢"，他会说"办完了" —— **假结果比没结果更坏**。

### ② 必须撤位置覆盖，且 `abort` 先、`drop` 后

`working` 期间他的位置被 `roam.put()` 压在目的地。不撤 ⇒ "叫回来了"却还站在外面。
顺序反了 ⇒ 撤覆盖那一刻差事还在表里，**下一拍**又会把他压回去。

### ③ 没点名就不猜

| 情况 | 行为 |
|---|---|
| 点名 + 那人在办 | 撤那一条 |
| 点名 + 那人**没**在办 | **不拦**（交给普通对话，别替用户"取消"不存在的事） |
| 没点名 + 恰好 1 条在办 | 撤（人话里很少把名字说全） |
| 没点名 + ≥2 条在办 | **不拦**（不猜是谁） |

## 5. 两条教训（都是**我自己的判据**先错）

### ① `C3` 第一版是**恒真**——被一条既有规则顺手救了

第一版：

```python
_hc3 = _Host()                                    # 说话人默认 = ralsei
_hc3.handle_errand_command('别让 ralsei 去 oneshot 了')
```

它测的是"这句话**不该**被派出去"。看着挺对，但 `_errand_parse_intent` 有一条
**既有**规则 ④「不能派自己」—— 而说话人恰好就是 `ralsei` ⇒ 那句话**本来就会被挡掉**，
跟否定闸一点关系都没有。
`mutate152 M4`（把否定闸拆成 `if False:`）实得"**无**"变红，当场拆穿。
⇒ 说话人换成 `susie` 才是干净对照：拆掉否定闸 ⇒ 苏西一开口，ralsei 真被派出去了。

### ② `M8` 期望**写宽了**——`board.enabled` 有两层

我原以为"关闸就别撤"只有一处检查，写期望时把 `A6` 和 `B8` 都列上。
实得只有 `A6` 红 —— 因为**解析层**也有一处 `enabled` 检查（它负责"关闸之后这句话
就是普通聊天，不许被吞掉"），由 `B8` 单独守。
⇒ 不是"同一件事两处算"，是**两个责任**：解析层不许吞聊天 / 动作层不许动手。
拆一层只该红一条 ⇒ 补 `M8b` 专拆解析层。

### ③ 抽出"共用规则"会**撞旧夹具**——而且撞出一个更大的问题

把"名字查找"抽成 `_errand_find_name` 之后，全量 G2 立刻红一条：

```
check150   exit=1  PASS=53（原本 104）
AttributeError: '_ParseHost' object has no attribute '_errand_find_name'
```

**不是产品坏了，是夹具比产品旧**（第107轮那条教训的同型）：`check150` 的
`_ParseHost` 只装了三个协作者，产品多了一个 ⇒ 桩没跟上。
修法是**给桩补一行**，不是回退产品（否则"规则只有一份"就破了）。

顺手按同一条线索查了 `check114`（第114轮那套差事门控锁）—— 它也崩在同一个地方。
更值得记的是：**`check114` 从来没进过 `SUITES`**（`grep check114 run_all.py` = 0）。
也就是说它写了、跑了、**一直没人跑**，它守的东西等于没有。
这正是第115轮踩过的坑（守卫没登记 = 守卫不存在）。
⇒ 本轮把它**补登记**进 `SUITES`（`84/0`），这也是它第152轮唯一的改动。
